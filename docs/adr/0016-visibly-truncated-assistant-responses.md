# ADR-0016 — Visibly truncated assistant responses through T4 (narrow, dev-only exception to ADR-0015 point 2)

**Status: Accepted** by the owner on 2026-10-24, for the dev-only external llama.cpp adapter `llama-dev-http` ([ADR-0015](0015-dev-only-external-llama-runtime-adapter.md)) and the additive SQLite migration 0003 only. Not an access-capable build, not Windows, not a V0 acceptance. It **amends ADR-0015 point 2 and the acceptance criterion in point 1**, and the LD-04 §3.3 P4 / §3.4 wording as a narrow scoped note; it supersedes nothing else and changes **no** LD-04 classification and no B3/B4/B5 interpretation.
**Date:** 2026-10-24.

## Context

The first attended real-Qwen smoke ([evidence](../evidence/v0-1-first-real-qwen-smoke.md)) sent three messages; the third generation reached `max_tokens` 384, arrived at the worker as a complete HTTP delivery with an incomplete finish, was rejected as `output_truncated` by ADR-0015 point 2, closed `indeterminate` and **quarantined the disposable dataset for good**. Ordinary use meets this quickly, and the rule costs the whole dataset for a condition that is not transport or identity uncertainty.

Existing contracts relevant to the decision:

- ADR-0015 point 1: T4 completion means **accepted response delivery**, not process termination, idleness or B3; "accepted" required `finish_reason: stop`. Point 2: a truncated, empty, mismatched, unsaved or late response manufactures no settlement evidence and quarantines, "deliberately including a plain `finish_reason: length`".
- LD-04 §3.3 P4: "Truncation or an output limit is not natural completion: not published in 0B"; §3.4 lists `output_truncated` as a rejected, B3-settled code for adapters that declare B3.
- The T4 store write needs only an open fence, `STARTED` and epoch `0b`; it never consults `declared_bases`, and stamps `termination_basis = runtime_reported_terminal`, `completion_observed = yes` (what ADR-0015 point 1 already defines as "accepted response delivery").
- `Completed` is constructed by `LlamaHttpRuntime.await_result` **only after** HTTP 200, a complete and unambiguously framed body, a parseable chat completion and a re-verified sole listener (same pid and start time). Every other outcome is `Failed(POSSIBLY_ACTIVE)`. The smoke showed the truncated case arriving as such a `Completed` (the run's `closure_reason` was `runtime_failure`, which only a rejected delivery produces, not `connection_lost` or `deadline`).
- Messages are immutable by trigger and have no field that can carry the property; `completion_observed` is a closed `yes/no/unknown` set that already means "output observed" (it is `yes` for `output_truncated`); `termination_basis` is a closed set; `provenance_json` is immutable after dispatch; changing the stored text would alter source history (INV-006) and leak into future context.

## Decision

1. **Complete delivery is not complete answer.** The transport and identity facts that make a delivery attributable (point 5) are independent of whether the model's answer ended naturally. A delivery whose finish reason is exactly `length` is a **semantically truncated answer delivered completely**. It is neither a transport failure nor an unknown runtime state.
2. **Narrow exception to ADR-0015 point 2.** A `Completed` delivery from an adapter that explicitly marks it `limit_reached`, with non-empty content, from the verified bound instance whose model label equals the binding, publishes through the **existing T4 path** with message completeness `truncated`. Only `llama-dev-http` sets the mark, and only for the exact finish reason `length`. ADR-0015 point 1's acceptance criterion is read accordingly: "complete (`finish_reason: stop`)" becomes "complete in framing and attribution, with `stop` published as normal and exactly `length` published as truncated".
3. **T4 claims nothing more than before.** `termination_basis = runtime_reported_terminal` and `completion_observed = yes` on such a run still mean *accepted response delivery* (ADR-0015 point 1). They do **not** mean the generation completed naturally, the process terminated or is idle, B3 qualification, cancellation or late-delivery exclusion; the slot is released exactly as for any T4 success. The **message's completeness** is the only authority on whether the answer ended naturally. `finish_reason` is used as a **content label only**, never as lifecycle or release evidence; the LD-04 `finish_reason` register row stays `BLOCKED_BY_RUNTIME_EVIDENCE`.
4. **Delivery contract.** `Completed` gains `limit_reached: bool = False`. `complete=True` with `limit_reached=True` is **invalid** and raises at construction (an adapter fault, which the supervisor treats as possibly active and quarantines). `complete=False` with `limit_reached=False` keeps its existing meaning: an incomplete result of unknown kind, **rejected** as `output_truncated` exactly as before. Scripted and in-process adapters never set the mark, so their behaviour is unchanged.
5. **Unchanged fail-closed paths** (each still quarantines or settles exactly as before): HTTP non-200; malformed JSON; missing or non-string content; short, truncated-chunked, close-delimited, invalid, duplicate or conflicting `Content-Length` framing; `Content-Length` with chunked coding; dropped connection; deadline; a changed, vanished or shared listener or a changed process; a partly written request; a model-label mismatch; **empty content with any finish reason**; a missing, null or unrecognized finish reason (anything other than exactly `stop` or `length`); a late or lost-race delivery after closure (discarded, still quarantined by the existing guard); every B3/B4/B5 restriction for `EXTERNAL` bindings in `apply_evidence` and in the store's settlement transaction.
6. **Additive persistence (migration 0003).** `messages.completeness TEXT NULL` with `CHECK (completeness IN ('complete','truncated'))`, written in the T4 `INSERT`, so it commits atomically with `succeeded` and a failed publication leaves neither. `NULL` means *unclassified*: every user message and every assistant message that existed before 0003; **nothing is backfilled and no completeness is invented**. A trigger refuses a non-`NULL` value on a user message; the existing immutability trigger covers the new column. A normal complete delivery records `complete`; a direct store caller that does not say records `NULL`. The migration rewrites no row and changes no existing trigger. The preserved read-only smoke dataset is never opened or migrated by this work.
7. **API and UI.** `MessageDto` gains the additive `completeness` (`complete`, `truncated` or null) in conversation detail, submission results and replays. The client shows the text notice *"This reply was cut off at the model's output limit."* only when the persisted message is `truncated`, never from run status, `completion_observed` or client state, so it survives reload, application restart and replay; legacy messages stay unlabelled; the composer stays available; the message text is not altered. A truncated run is `succeeded`, so it is not retryable; the user continues with a normal message.
8. **Context.** `ContextBuilder` is unchanged: it sends role and content only, so a truncated reply goes to the model verbatim and the marker is never part of model input, the golden fixture or the configuration digest (ADR-0014 is not triggered). Truncated replies consume the input budget like any other history; the 1400-character history cap (and the joint budget) stays a separate usability limitation. Future bounded context selection must treat `completeness` as message metadata, count it against its budget and record in its view's provenance that a truncated message was included as is.
9. **Scope and residual risks.** Development only, `llama-dev-http` only, synthetic data only. Real Qwen verification of the new behaviour is **NOT TESTED** (this decision was implemented and verified with fake HTTP only). `length` also covers a context-full stop, so the notice says "cut off", not why. The finish-reason evidence is thin (E2-B one `length`, the smoke one rejected `length`). A truncated reply may end mid-sentence, mid-word or mid-code. No regenerate or continue feature exists. The attribution residual of ADR-0015 point 10 is unchanged.
10. **Classifications untouched.** No LD-04 row is promoted; E1, E2-B, E3 and smoke evidence are not edited; ADR-0015's other points stand.

## Alternatives considered

- **Keep quarantining `length` (ADR-0015 point 2).** Rejected by the owner after the smoke: it costs a whole dataset for a content-limit condition that is not transport or identity uncertainty.
- **Settle the rejected delivery through B3 to release the slot.** Rejected: it manufactures a basis the binding never declared (ADR-0015 revision 1 rejection stands). This decision publishes through T4 instead and settles nothing.
- **Mark truncation in the text** (an appended notice). Rejected: alters source history (INV-006) and would be sent back to the model.
- **Reuse `completion_observed`, `termination_basis` or `provenance_json`.** Rejected: closed sets with other meanings, or immutable after dispatch.
- **A run-level column instead of a message-level one.** Rejected: the property belongs to the text, travels with it through branching, export and future context selection, and is readable from the same `HistorySource`.
- **Backfill older assistant messages as `complete`.** Rejected: invents a fact for messages whose finish was never recorded.
- **Treat every `complete=False` delivery as a truncation.** Rejected: unknown or missing finish reasons would be published as an accepted truncation. Only an explicit mark from an adapter, set only for exact `length`, publishes.
- **A new termination-basis value for truncated delivery.** Rejected: a closed set that would need its own migration and implies a lifecycle meaning this decision does not claim.
- **Raise `max_tokens` or the context instead.** Not an alternative: a different lever (the Q5 configuration step and the launch profile); neither removes cutoffs.

## Consequences

- Hitting `max_tokens` no longer quarantines the dataset **when the delivery satisfies point 2**; the user sees the reply with a visible notice. All other ADR-0015 quarantine conditions remain.
- `termination_basis = runtime_reported_terminal` on a succeeded run must still be read as ADR-0015 point 1; later reports must not read a truncated success as natural completion, B3 qualification or runtime idleness.
- Accepted truncated replies lengthen history, so the history cap and joint budget become the binding limit sooner (a pre-dispatch `context_exceeds_capacity` refusal, not a quarantine). Bounded context selection with visible omission is the natural next step and is not part of this decision.
- Schema version becomes 3. Existing datasets migrate additively on open; the preserved smoke copy (mode 0400) is not opened by this work.
- Unchanged and not accepted here: streaming, cancellation, control during generation, per-attempt registration, B3/B5 qualification, late-delivery exclusion, regenerate or continue, memory, personas, bounded context selection, authentication and access containment.
