# V0 Persistence Technology Evaluation v0.1

**Status:** Requirement-level recommendation complete; final technology selection deferred pending the existing actual-host evidence gate. No selection ADR created.  
**Date:** 2026-10-04.  
**Owners:** Architect and Data & Memory; focused Backend, Security, Operations and QA author reviews.

## 1. Recommendation and decision boundary

**REQUIREMENT_LEVEL_CONCLUSION: recommend SQLite for V0.** Its transactional capability fits Anonymous's coherent history/execution/access operations, and an embedded engine avoids another service, database credential boundary and listener. The reason is the actual one-authoritative-server workload with several clients and short persistence operations, not merely “single user.” PostgreSQL is a strong alternative and likely migration target if measured write contention or future worker requirements justify its additional operation. MongoDB is technically capable with an appropriate transactional deployment, but its document flexibility does not remove this project's cross-object consistency and provenance obligations.

**HOST_VERIFICATION_STILL_REQUIRED: this is not a finalized selection.** The [logical model's Persistence Technology Requirements](../05-data-model.md#persistence-technology-requirements) explicitly require actual-hardware resource/capability validation before selection. Windows has not been inspected or exercised, and no database experiment is authorized here. This evaluation preserves that gate rather than silently changing it. Sections 13–14 identify the precise remaining evidence, separate selection prerequisites from later implementation tests, and explain how to conclude the decision. No selection ADR is warranted yet; ADR-0004/0012 remain binding.

| Candidate | Classification | Meaning |
| --- | --- | --- |
| SQLite | RECOMMENDED_V0; REQUIRES_MORE_EVIDENCE | First candidate to validate. Documented requirement fit is strong; actual host/build/resource evidence is missing. |
| PostgreSQL | VIABLE_ALTERNATIVE; FUTURE_MIGRATION_TARGET; REQUIRES_MORE_EVIDENCE | Can satisfy V0, but no current workload need justifies preferring its service/administration cost. Actual Windows suitability is also unverified. |
| MongoDB | NOT_RECOMMENDED_V0 | No V0 advantage sufficient to offset transactional deployment, relationship enforcement and operating costs. Not fundamentally incompatible; revisit only with a changed workload and evidence. |

No additional database has a demonstrated material advantage for this scope. This document evaluates products, not physical schemas, query designs or deployment configurations. It selects no journal mode, timestamp datatype, identity encoding, ORM, migration library, vector store or application framework.

## 4. Candidate capability evidence

### 4.1 SQLite

SQLite runs within the application process and adds no separate database daemon or mandatory network protocol. That reduces setup/exposure but also means it supplies no independent database-process isolation from the application. File access permissions are the important local boundary. [SQLite serverless architecture](https://www.sqlite.org/serverless.html).

SQLite supports atomic transactions; their durability depends on operating-system/filesystem behavior and selected settings. These are suitable building blocks for the logical coherence boundaries, not proof an unspecified adapter already fulfills them. [Atomic commit](https://www.sqlite.org/atomiccommit.html).

It permits one writer at a time per database, while a server can serve many application clients. This matches the proposed short-write workload in principle; it does not establish acceptable busy time under load. [Appropriate uses](https://www.sqlite.org/whentouse.html). WAL can allow readers alongside a writer; checkpoint delays, long readers and busy outcomes still matter. WAL is evaluated as a capability, not selected here. [WAL documentation](https://www.sqlite.org/wal.html).

Relational constraints and query capabilities suit cross-object references. Foreign-reference enforcement must be verified for every application access path rather than assumed from declared rules. Flexible metadata is supported by JSON facilities; SQLite JSONB is not PostgreSQL JSONB interchange. [Foreign-reference enforcement](https://www.sqlite.org/foreignkeys.html), [JSON facilities](https://www.sqlite.org/json1.html). No physical constraint or metadata layout is designed here.

**Version evidence gate:** SQLite documents a WAL-reset corruption bug fixed in 3.51.3 and later, with backports including 3.44.6 and 3.50.7. It concerns concurrent write/checkpoint activity across connections. Any proposed WAL build must demonstrate the fix and current maintenance status in the **library actually used by the driver**; a Python version or separate command-line executable is insufficient. No installed library was inspected or declared vulnerable. [WAL-reset notice, section 11](https://www.sqlite.org/wal.html).

### 4.2 PostgreSQL

PostgreSQL provides transactional changes and multi-version concurrency, with stronger isolation options where application invariants require them. Default Read Committed does not make a multi-step read/check/write sequence automatically serializable; transaction conflicts and serialization failures need controlled handling. [Transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html).

Its relationship constraints, flexible JSON facilities and recursive query support provide a strong fit for structured provenance plus evolving metadata. Those capabilities do not automatically prevent derivation cycles, preserve immutable history or decide access authority. [JSON facilities](https://www.postgresql.org/docs/current/datatype-json.html), [recursive queries](https://www.postgresql.org/docs/current/queries-with.html).

A separately managed database service offers a distinct process/privilege boundary and more concurrent-write headroom, but adds startup readiness, authentication, maintenance, resources and failure modes. A self-managed local deployment needs no cloud service. Official Windows distribution exists, with a release-specific tested-platform list; that is not evidence for the unknown Windows desktop version. [Windows distribution](https://www.postgresql.org/download/windows/).

Its added capability becomes valuable when sustained concurrent writes, independent workers or recovery objectives actually demand it. Several browser sessions and slow inference alone do not establish that need, because neither should hold a database transaction open for the generation duration.

### 4.3 MongoDB

MongoDB offers atomic operations within a document and multi-document transactions on eligible replica-set/sharded deployments. Ordinary standalone deployments do not supply those transactions. The official production transaction guide calls for a multiple-node replica set; any proposed smaller topology would need explicit release-specific support/capability evidence, not an assumption that “one server” means standalone transaction support. [Atomicity](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/), [transaction deployment considerations](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/).

This evaluation does not choose a collection/document layout or require distributed application authority. The issue is whether all facts in an Anonymous coherence boundary can commit together across whichever physical units are eventually chosen. Forcing all history into one indefinitely growing document to avoid that question is not a valid argument: BSON documents have a 16 MiB limit, and the domain contains shared references and independently evolving access/execution state. [Document limits](https://www.mongodb.com/docs/manual/reference/limits/).

Flexible documents can be validated, and aggregation can follow relationships. Validation does not supply relational-style cross-object referential integrity automatically; Anonymous would still need transactional checks and validation of referenced identities. Journal/read/write concern and commit acknowledgement affect what can safely be confirmed. An acknowledgement timeout is not proof a write never took effect. [Validation](https://www.mongodb.com/docs/manual/core/schema-validation/), [write concern](https://www.mongodb.com/docs/manual/reference/write-concern/).

Self-managed Community deployment can operate locally without Atlas. Its daemon, authentication and transaction topology increase the operating burden relative to an embedded engine. Windows installation is documented, but selected release/edition/platform support must be checked against the actual host. [Windows deployment documentation](https://www.mongodb.com/docs/manual/administration/install-community-windows/). Documentary capability is not a benchmark or an endorsement of an unverified topology.

All three can support requirement-level consistency with an appropriate design; none can promise exactly-once physical model execution. Retrying a database-only transaction after a proven rollback differs from replaying a user intent or an external inference. Automatic driver callbacks must never wrap a model invocation or protected response delivery. Unknown commits require reconciliation of the same operation, not a newly identified substitute.

FR-15's authoritative commit instant is not automatically supplied by a function named “now,” a transaction-start clock, an identifier timestamp or engine replication metadata. Later design must define how the application associates the absolute instant with coherent publication and verifies precision/clock behavior, without retimestamping after uncertain acknowledgement. No timestamp representation is selected here.

## 6. V0 concurrency versus future scale

**V0_CONCURRENCY:** Windows/Mac/iPhone sessions may list/open concurrently, submit nearly together, retransmit the same request, act from stale history or receive background completion. One authoritative application arbitrates current policy and admission; database work must be bounded so it does not starve revocation or reads. Generation is long-running external work between persistence operations, not a long write transaction. Short storage lock waiting is not permission to queue a new generation while the conversation is busy.

SQLite's main trade-off is serialized writes, including writes for unrelated conversations/security state. Multiple readers are feasible, subject to transaction mode and bounded read duration. The decisive evidence is actual write wait, failed/busy outcomes, checkpoint behavior and revocation responsiveness under representative load—not a theoretical user count. PostgreSQL can overlap more independent writes but still contends on shared state and still needs an application admission protocol. MongoDB can likewise serve concurrent requests, with transactional conflict handling and acknowledgement concerns rather than an automatic correctness advantage.

Stale clients cannot place messages at old positions or retry superseded requests. A database read snapshot gives a coherent view at some point; it never freezes authorization for subsequent delivery. Across all candidates, current access must be re-evaluated and committed order must come from Anonymous, not result arrival order, physical scan order or timestamps.

**FUTURE_SCALE_CONCURRENCY:** Independent background writers, extraction jobs, indexing, multiple application processes or sustained simultaneous conversation activity may make SQLite contention unacceptable. Prefer preserving one authority and measuring first; if new worker/topology requirements justify it, PostgreSQL is a natural candidate. Adding compute nodes does not by itself require another database writer. More users are a future authorization/product change, not justification for immediate sharding. No numeric throughput threshold is asserted without an agreed workload and actual measurements.

## 7. Relationships, historical boundaries and flexible metadata

All candidates can represent relationships between persistent identities without turning a conversation into a single mutable transcript. SQLite/PostgreSQL offer relational joins and recursive traversal; MongoDB offers reference-oriented aggregation and recursive graph lookup. These are query capabilities, not proposed structures. Graph-shaped domain data does not require a graph database. [SQLite recursion](https://www.sqlite.org/lang_with.html), [PostgreSQL recursion](https://www.postgresql.org/docs/current/queries-with.html), [MongoDB graph lookup](https://www.mongodb.com/docs/manual/reference/operator/aggregation/graphlookup/).

The application must distinguish message ancestry, actual input contribution, triggering-request association and producing-run association. Navigation in two directions is not a derivation cycle. Future cycle prevention needs a coherent check against competing relationship changes; a recursive query or foreign-reference check alone does not guarantee a DAG. No candidate removes that obligation.

A retained V0 boundary resolves a fixed committed prefix and exact message forms. A future merge must preserve each source's historical frontier and create a new identity while sources continue evolving. Future edits need recoverable prior forms. All three can accommodate this evolution without redefining current history; MongoDB denormalization would need particular care to avoid divergent copied source facts, and relational references still need correctly scoped historical meaning. No Branch entity, revision identity policy or merge representation is selected.

Flexible runtime parameters, provenance extensions, client observations and future tools/Memory metadata are plausible in all three. SQLite JSON facilities and PostgreSQL JSON support mean flexible metadata does not uniquely favor document storage. MongoDB's flexibility is useful for heterogeneous bounded content, but explicit application validation and versioning remain necessary. Required ownership, provenance, lifecycle and admission facts cannot become unchecked optional metadata merely because a storage format permits missing values. Distinguish absent, unknown and explicit empty values; retain unknown future metadata through a controlled migration where its meaning permits. No physical JSON/BSON layout is prescribed.

## 8. Schema evolution and Python integration

Long-lived history requires explicit versioned evolution and compatibility checks for every candidate. “Schema flexible” does not mean “migration free.” A migration must preserve source bytes, stable identities, instants, order, historical boundaries, original authorship and run/provenance links. An incompatible reader must refuse or report incompatibility rather than fabricate empty history. Forward transformation, interrupted migration and safe recovery need deliberate design; arbitrary downgrade is not a recovery plan.

Relational migration ecosystems are mature; tools commonly abstract both SQLite and PostgreSQL, with engine-specific limitations that remain visible. MongoDB has migration approaches too, but flexible-document validation/backfill and cross-reference verification still require application discipline. Tool availability earns feasibility credit only; **no ORM or migration library is selected**. Database drivers and typed application models have separate responsibilities: typed wrappers do not enforce durable referential or lifecycle invariants.

Python's leading status does not dictate sync versus async, transaction ownership or worker implementation. Those choices must keep blocking persistence out of latency-sensitive access/delivery paths without scattering engine objects through the application. Mac Python availability lowers experiment setup friction but does not establish the linked SQLite version, native driver build or Windows compatibility.

All candidates can operate without a mandatory cloud service after provisioning. Offline provisioned Windows application use remains a requirement; remote clients still need network/server availability. Installing a database on the Mac would create only an isolated development fixture, never a second production writer.

For network-capable databases, bind/expose only the approved server-local application path and require authentication/least privilege. Loopback reachability alone is not caller identity, and Tailscale membership must not grant database access. No database, administration or replication endpoint belongs on the LAN/overlay/public client surface. PostgreSQL supplies configurable client authentication; MongoDB documents authentication, access restriction and transport/storage controls. [PostgreSQL authentication](https://www.postgresql.org/docs/current/client-authentication.html), [MongoDB security guidance](https://www.mongodb.com/docs/manual/administration/security-checklist/). No database security configuration is performed or selected here.

An embedded engine reduces network surface, not the need for OS protection. Ordinary SQLite files are not inherently encrypted; encryption is a separate capability/product decision, which this task does not make. [SQLite encryption distinction](https://www.sqlite.org/see/doc/trunk/www/readme.wiki). Likewise database authentication or journaling does not prove encrypted storage for the other candidates. Preserve the accepted Windows service-identity/ACL/DPAPI boundaries; DPAPI custody of usable secrets does not encrypt all conversation history. Actual Windows disk protection, service-profile behavior and independent key custody remain deployment gates. Mac FileVault proves nothing about them.

Protect backups, exports, temporary files, journals, diagnostic traces and crash reports with the same PRIVATE treatment as source data. Avoid credential/query/payload leakage in ordinary logs. A database administrator or privileged host compromise remains outside the existing confidentiality guarantee; adding a daemon does not defeat trusted host administration. None of this chooses an encryption product or relaxes the runtime's prohibition on ambient source/secret access.

## 10. Backup, export, recovery and portability

Full backup design remains deferred, but each candidate must permit consistent capture and verification of history plus the facts that make it attributable and safe to resume.

For every engine, consistent database capture is only part of a consistent Anonymous recovery package. Installation binding, OS-protected secrets, recovery proof custody, runtime/publication uncertainty and security anti-rollback need separate handling. A restored old revocation/credential state must not revive authority; a fresh session boot generation alone is insufficient. Storage portability does not make DPAPI-bound usable secrets portable without explicit re-provisioning or a separately authorized transition.

V0 guarantees application-process restart with intact accessible storage, not a recovery-point/time objective, full disk-loss recovery or power-failure protection. Engine durability features can exceed that minimum but do not silently expand the guarantee. A later restore/host move must establish that the original writer is stopped and prevented from resuming; unknown old authority blocks activation. None of the three engines makes independent copied datasets safe to activate in parallel.

## 11. Future growth, search and migration analysis

### 11.1 Search and likely growth

SQLite offers FTS5 where included in the build; PostgreSQL has full-text search and separately maintained vector extensions such as pgvector. These are capability examples, not extension or vector-store selections. [FTS5](https://www.sqlite.org/fts5.html), [PostgreSQL text search](https://www.postgresql.org/docs/current/textsearch.html), [pgvector project](https://github.com/pgvector/pgvector).

MongoDB offers self-managed text search and separately deployed Search/Vector Search capabilities. Current self-managed `mongot` documentation lists Linux targets, not native Windows/macOS; local Docker development is not equivalent to supported production deployment. Do not count Atlas branding or a preview/development path as evidence of a free native Windows V0 feature. [Self-managed text search](https://www.mongodb.com/docs/manual/core/indexes/index-types/index-text/), [self-managed search compatibility](https://www.mongodb.com/docs/search/self-managed/current/deployment/compatibility-requirements/). This limitation is a future integration cost, not a V0 blocker because retrieval is deferred.

All three can supply eligible source identities/content/boundaries to a separately scoped search/vector sidecar. An extension or sidecar must preserve PRIVATE access, provenance, rebuild/freshness rules and explicit correction semantics. A search result is not canonical history and cannot authorize access. No cloud embedding, vector store, synchronization method or Memory subsystem is selected.

Larger history alone does not prove SQLite incompatible. Measured lookup/maintenance/backup duration and write contention matter. Files/artifacts have separate logical identity/content-storage responsibilities in the domain; future bytes need not all share the conversation persistence mechanism. Richer Memory, branch/merge and background work can be added while preserving sources, but require new design and resource evidence. Additional compute nodes do not transfer history ownership. Optional multi-user capability changes permission and workload requirements and warrants re-evaluation rather than extrapolation from V0.

### 11.2 Migration paths and nontrivial risks

| Path | Plausible reason / retained boundary | Main migration work and risks |
| --- | --- | --- |
| SQLite → PostgreSQL | Sustained writer contention, independent workers or operational recovery needs; C08 implementation changes behind the same semantic ports. | Translate engine-specific representations, transaction/conflict behavior, precision/time conversion, flexible metadata and query semantics. Check null/absent values, comparison/collation and case sensitivity; SQLite's permissive behavior may expose previously invalid data under stronger target constraints. Retest every coherence and restart case. An ORM does not make this automatic. |
| SQLite → MongoDB | A future demonstrated bounded-document workload provides a material advantage, not simply “chat looks like JSON.” | Redesign physical aggregation in a later task, map all references and historical boundaries, preserve atomically published meanings under document/transaction limits. Avoid duplicating history into mutable copies or deriving identity/order from engine defaults. Validate any JSON/BSON conversion and access-state representation. |
| MongoDB → PostgreSQL | Relationship integrity, reporting or operating economics favor a relational service. | Discover historical document variants, absent versus null meanings, embedded/copied facts and implicit reference conventions; reconcile anomalies explicitly without rewriting authoritative history. Map references, preserve precision/order/provenance and reconstruct equivalent transaction outcomes. Not a direct dump import. |
| PostgreSQL → another primary or specialized stores | Different proven deployment/resource needs or dedicated retrieval/artifact capability. | Translate types/functions/extensions and isolation behavior, preserve application identities, and validate complete source equivalence before primary cutover. A specialized derived sidecar can coexist without moving canonical ownership; building it is not migration of authoritative history. |

All paths need an inventory of source and generated historical content, run/input attribution, historical boundaries, accepted-intent associations, unresolved execution and current access state. Preserve exact committed bytes and instants; do not regenerate responses, renumber domain identities or sort by timestamps. Verify counts **and** contents/relationships/outcomes; equal counts alone are insufficient.

A future controlled transition needs a consistent source capture, verified transformation and validation on an inactive target, with a protected original retained. It must explicitly handle failures and current security state before activation under ADR-0012. Rolling application binaries back after new target writes cannot simply restore an old data copy without losing history/revocation changes. Rollback/recovery implications are reasons for a future migration plan, not a complete backup/cutover design here.

Reconsider when measured write contention/latency prevents the agreed workload, maintenance exceeds usable downtime, resource/backup/restore objectives change, independently writing workers become necessary, host/platform support fails, or changed product scope makes another engine materially simpler. There is no guaranteed eventual migration: “may require migration under growth” is different from “fundamentally incompatible with V0.”

## 13. Explicit recommendation, accepted trade-offs and lock-in rules

1. **Which should Anonymous use?** SQLite is the recommended V0 technology subject to G-01–G-03 below. Final selection is deferred, not silently accepted through the ranking.
2. **Why?** It supplies credible transactional/relationship/evolution capabilities within a single protected server-local application. No present requirement needs the additional service and concurrent-write capacity of PostgreSQL. MongoDB's metadata flexibility is also available without changing to document storage, while its transaction topology and reference checks add cost here.
3. **What trade-offs would selection accept?** A serialized writer, explicit busy/checkpoint discipline, limited independent process isolation, more work for some structural changes and a possible later migration. These are proposed trade-offs, not measured proof they are harmless.
4. **What kind of commitment?** A future accepted SQLite ADR should call it a **replaceable V0 implementation choice**, not a durable architectural dependency. Durable commitments are preserved meanings, ownership, authority and C08 contracts.
5. **When reconsider?** Use the measured workload, operational and product triggers in section 11; do not migrate solely because another engine has more features. A failed eligible-local-storage prerequisite blocks deployment for all candidates, not permission to put SQLite or another primary store on a network/synced folder.
6. **How prevent lock-in?** Keep engine query objects, storage identifiers, driver exceptions, connection/transaction handles, document shapes and extension-specific semantics inside C08. Ports express purpose-specific coherent operations and known/failed/unknown outcomes, not universal CRUD or vendor methods. C03/C04/C05/C09 own authorization, identity, ordering, admission and retention. Preserve neutral semantic export and adapter contract tests; do not promise cost-free migration or implement two production adapters now.

Historical SQL/JSON/BSON representations must never become application-level identity, timestamp ordering, provenance authority or a client contract by accident. A database dependency may be replaceable even when its later physical design uses appropriate engine capabilities; portability does not require avoiding every useful feature, only containing it and documenting the migration cost.
