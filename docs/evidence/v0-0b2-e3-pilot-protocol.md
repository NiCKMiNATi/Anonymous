## 1. Question and scope

With the pinned `llama-server` b11440 (single model, E2-B no-fork launch configuration), when the **owner process is SIGKILLed while a generation is observably in progress**:

- **O1** does the runtime survive (OS-visible facts only)?
- **O2** does it exit by itself within the bounded window?
- **O3** can a **Successor that holds only the persisted record path** classify it over time without ever calling it `PROVEN_TERMINATED` while it lives?
- **O4** after a kill by verified identity, does the Successor reach the **non-parent** exit conjunction (section 9), and how long does that take?
- **O5** does the one in-flight request, left undisturbed, still complete at its independent Reader? (observation of one attempt; section 2)

It is **one lifetime**. Nothing from it is a rate, a reproducibility result or a general claim.

Out of scope: V2 or any series, any HTTP request to the runtime after the owner kill, adoption of the orphan for generation, Option C, A/B lifetimes, router mode, a supervising shim or any owner-death mechanism, retry or a second lifetime, application integration, the `.partial` model file, and the choice of the permanent controller architecture.

## 3. Roles, processes and record writers

| Role | Process | Does | Never does |
|---|---|---|---|
| **Driver** | stable parent, never killed by the experiment | authorization and pins checks; E2-B Phase 1 gate and Phase 2 controls; creates the key file; consumes the authorization; starts the Owner; **runs the S1–S13 monitor for the whole lifetime, owner alive or dead**; starts the Reader; polls `/slots`; evaluates the trigger; SIGKILLs the Owner (only); deletes the key file; starts the Successor; bounds the window; backstop; writes the evidence | any HTTP to the runtime after the owner kill; signalling anything not identified by (pid, kernel start); `killpg` |
| **Owner** (`e3_owner.py`) | child of the Driver, own session | launches the runtime exactly as E2-B does (it inherits `Instance.argv`/`env` unchanged: same flags, sandbox profile, environment, stdin at `/dev/null`), `INTENT → SPAWNED → BOUND`, reports on stdout, then **idles** | hold the API key; poll; request; write a record, create a file or open a connection while idle |
| **Reader** (`e3_reader.py`) | child of the Driver, sandboxed with the E2-B loopback-only profile | sends the **one** generation request over **one** connection (no retry, no reconnect, no second request), waits for the response or its 90 s absolute deadline, reports metadata (status, completion, lengths, content hash) | close the connection on purpose; cancel; send anything else; print response text |
| **Successor** (`e3_successor.py`) | fresh process started by the Driver after the kill, argument = **the record path only**, under a kernel network denial and read denial | classifies by OS facts only; at the end of the window terminates by verified identity through the signal ledger; verifies the non-parent conjunction; writes the final record state | open any socket, make any HTTP request, read the API key, fixtures or model, use waitpid, signal an unidentified process |

Why separate: owner death must not also be requester death (that would be a disconnect observation); the monitor and the backstop must not die with the owner.

**Record writers.** The execution record (E2-B store, one JSON file per instance) is written by the Owner until it reports `BOUND`, then by the Driver (annotations) and, after the owner kill, also by the Successor (final state) or the Driver's backstop. All writers use `LockedRecords`: a cross-process lock plus a fresh read of the on-disk record before every write, so a stale copy cannot lose an update and `owner_review_required` stays sticky across writers. The Owner performs **no write** between `BOUND` and its death (a SIGKILL during a write would leave a `*.tmp.*` file that blocks new runs); a test inspects the idle loop. A quarantine is sticky: only the owner-directed `recover` tool clears it. **A mandatory quarantine survives the failure of its own write.** The bounded record lock can make the write of `owner_review_required` fail (a stalled holder). The Driver then keeps the intent (the pending review, the in-memory record and the quarantining stop itself), marks the failure, and from then on (a) stops its own child, the Successor, so that no other writer can resolve the record without the flag, (b) retries the write, and (c) applies the intent to the copy of the record that its own final write refreshes, so that final write is a `QUARANTINED`, never an `EXIT_VERIFIED`. If the flag still cannot be written, or the record was already resolved as `EXIT_VERIFIED` by a writer that had not seen it, no successful outcome is reported: the outcome is `QUARANTINE_NOT_PERSISTED`, `owner_review_required` is true and `owner_review_persisted` false in the report, and the record stays unresolved (or, in the second case, the report is the owner's only notice; a resolved record cannot be flagged by the harness).

## 4. Sequence and bounds

All durations use the kernel uptime clock. The values below are the production bounds (`e3_lib.BOUNDS`); the harness refuses to run if they are internally inconsistent (`check_bounds`).

| Bound | Value | Meaning |
|---|---|---|
| arming delay | 1.5 s | the request must have been in flight this long before a kill |
| `/slots` poll period | 0.1 s | Driver polling before the kill |
| consecutive processing polls | 3 (minimum) | |
| kill staleness | 0.2 s | the kill must follow the last qualifying poll within this |
| pre-kill abort | 20 s | request sent → trigger, otherwise abort |
| idle after Reader completion | 10 s | orphan observation ends this long after the Reader completed ... |
| orphan maximum | 60 s | ... or this long after the owner kill, whichever is earlier |
| Driver backstop | 75 s | after the owner kill |
| Successor TERM grace / KILL wait / verify | 3 s / 3 s / 4 s | the whole non-parent verification is inside this budget |
| backstop scheduling margin | ≥ 5 s | `backstop − (orphan maximum + TERM + KILL + verify)` must be at least this (`check_bounds`); production 75 − (60 + 3 + 3 + 4) = 5 s |
| backstop verify | 10 s | |
| shared lock wait | 2 s | every wait for the record lock or the signal-ledger lock is bounded by this (`lock_timeout_s`, at most 5 s, checked); a wait that times out sends or writes nothing and is reported |
| owner dead after SIGKILL | 5 s | |
| normal shutdown through the Owner (abort path) | 40 s allowance | |
| Reader absolute request deadline | 90 s | ≥ pre-kill abort + orphan maximum |
| overall lifetime ceiling | 300 s | monitor-enforced (S11) from the Owner's `SPAWNED`; shutdown may extend past it as accepted for E2-B |

Worst case by arithmetic (asserted by a test): readiness ≤ 120 s + bind 5 s + pre-kill 20 s + backstop 75 s + backstop verify 10 s = 230 s on the kill path; 185 s on the abort path; both below 300 s. The Successor's longest path is the longest window plus its TERM grace, KILL wait and complete verification (60 + 3 + 3 + 4 = 70 s), which leaves a 5 s scheduling margin inside the approved 75 s backstop; the inequality, including the verification time, is enforced by `check_bounds` and tested at its boundary. The verification loop can overrun its own limit by about one polling round plus the final classification (measured by a test to stay under 2 s), well inside the margin. (An earlier draft counted only the window, TERM and KILL, and left no room for a 7 s verification.) This arithmetic describes the **uncontended** Successor path. It is not a guarantee: a Successor that stalls (including while holding a shared lock) is not waited for beyond the backstop, which the Driver stops first. The Driver's orphan loop checks "Successor ended" and the backstop deadline first in every iteration, and every call in the iteration is bounded by its own limit (shared locks 2 s, `lsof` 3 s, `ps` 3 s), so the backstop fires at the first iteration at or after `t0` + 75 s: normally within about 0.2 s, at worst a few seconds later. **No hard cleanup deadline is claimed**: an OS-level stall (a process in uninterruptible state, a suspended or killed Driver, a sleeping machine) is outside what this code can bound; a child that cannot be reaped within 5 s after SIGKILL is reported (`successor_not_reaped`) and not waited for.

1. **Authorization and pins** (section 10), `--attended`, unresolved-record check, run lock. Refuse on any mismatch.
2. **Phase 1** (E2-B 61-sample Load Gate, AC, pressure 1, zero paging; unchanged code) and **Phase 2** (E2-B controls C1–C3; unchanged code). The spawn must start within 120 s of the end of the gate window. A failure ends the pilot with no runtime.
3. **Pre-spawn** (E2-B order): fixture G verification, artifact re-verification, swap baseline, monitor started and its first tick complete. The Driver creates the 0700 scratch directory and the 0600 key file.
4. **Consumption.** The authorization is consumed (exclusive create of `CONSUMED-<authorization id>`) immediately before the Owner is started. Immediately before that exclusive create the Driver verifies **again** every identity the authorization binds (the protocol document, the ten implementation files, expiry, single use, and that it is the same authorization id, plus the authorization's fixture hash against the pinned hash), because the first check precedes Phases 1 and 2 and the Owner, Reader and Successor scripts are read from disk only afterwards; any mismatch is a stop (`AUTH`) before consumption, with nothing started. **Fixture G is not re-read from the filesystem at this point.** The execution input is the in-memory body that `load_fixture_g` verified by exact length, full SHA-256, canonical form and structure earlier in the same run; that body, serialised canonically, is what the Reader sends (a test replaces the file after the verification and shows the request body is still the pinned one). From here a failed or missed pilot is not retried.
5. **Owner** starts, spawns the runtime, persists `INTENT → SPAWNED → BOUND` (binding verified: sole listener is the recorded pid on exactly `127.0.0.1:<port>`), reports. The Driver's monitor attaches at `SPAWNED`, so topology, RSS and egress are watched through the model load. The record is complete and durable before the Reader sends anything.
6. **Reader** sends the request. The Driver polls `/slots` (key in Driver memory) until the trigger (section 5) decides.
7. **Kill.** Before the signal: the on-disk record must be `BOUND` with a verified binding and the runtime's (pid, start) must equal the kernel's; the Owner's identity must be unchanged; then the Driver writes the **durable pre-kill section** (`e3`: scope, bounds, Owner identity, planned action, time; atomic write with fsync) and re-checks that no stop is active, the Reader has not completed and the trigger is still fresh (cheap early outs). The **authoritative check is inside the ledger's critical section**: the Driver asks the ledger to send SIGKILL to the Owner by pid and kernel start with a `precheck`, which the ledger runs after acquiring its (bounded) lock and after its own and the identity checks, as the last step before `kill(2)`. The precheck drains the queue (so a Reader completion that arrived while the lock was awaited is seen) and requires all of: no stop (the E2-B monitor's trigger list is read as well as `cancel`, because the monitor appends a trigger before its slower persistence and signalling and sets `cancel` only afterwards; an interrupt; a live monitor), the Reader not completed, the request's pre-kill bound not exceeded, arming delay and consecutive-poll eligibility, and a last qualifying poll no older than 0.2 s. Only then is the HTTP gate **closed** (from here the Driver sends nothing to the runtime) and the signal sent; `t0` is the instant of that actual attempt, taken inside the lock and written identically to the ledger and the record. Any refusal sends nothing, leaves the gate open, is recorded on the ledger as `precheck:<reason>` and ends as `TRIGGER_MISSED`, `TRIGGER_STALE` (with the reason: stale or timeout) or the stop that became active; a lock timeout is `E3-1` (not delivered). Then the key file is deleted. The Owner must be dead within 5 s, otherwise `E3-1`.
8. The Driver writes `t0`, the window deadline and the backstop time into the record, then **starts the Successor** (target ≤ 1 s after `t0`; measured, not enforced).
9. **Orphan window.** The Driver keeps the monitor running (S1–S13), samples the orphan's CPU time and connection list once per second (diagnostic) and watches the Reader. The window ends at the earliest of: owner kill + 60 s; Reader completion + 10 s; a stop (any S-stop, an operator interrupt, a dead monitor, **and a prohibited new connection (E3-3), published at the moment it is first seen, not after the window**). The Driver writes the updated deadline into the record (a failed annotation is reported and retried at most once per second; it never delays the backstop check); the Successor re-reads it. The Driver observes the runtime's connections and CPU time only while the recorded (pid, start) is verified live.
10. **Successor** classifies at `t0` + 0.25, 1, 2, 5, 10 s and every 10 s (OS facts only), registers a kqueue exit watch on the verified identity, and at the deadline sends SIGTERM through the ledger, waits 3 s, then SIGKILL through the ledger, waits 3 s, then verifies the non-parent conjunction (section 9) for up to 4 s and writes the final state. If the runtime exits by itself earlier, the Successor records that (O2) and verifies the same conjunction without sending any signal.
11. **Backstop** (section 8): at `t0` + 75 s, or when the Successor exits without resolving the record, the Driver stops the Successor (its own child), kills the runtime by verified identity and writes the final state itself, labelled `driver_backstop`.
12. **Close.** The Reader is killed (its own child) if still alive; key file removal is confirmed; the 60-sample post-unload window (E2-B rule); leftover scan; model file unchanged; committed view and raw-artifact hashes.

**Abort paths before the kill** (no retry, no owner kill): trigger not reached within 20 s (`PILOT_NOT_REACHED`), Reader completed first (`TRIGGER_MISSED`), trigger stale at the kill (`TRIGGER_STALE`), any stop, an operator interrupt, a runtime exit. The Driver asks the live Owner to perform the normal E2-B shutdown (`SHUTDOWN` command; if the Driver itself disappears the Owner sees stdin EOF and does the same). The authorization is already consumed.

## 5. Trigger: "observable active generation"

All must hold at the instant of the kill: the request has been in flight ≥ 1.5 s; `/slots` returned a non-empty list of objects with `is_processing` the **literal JSON boolean `true`** in ≥ 3 consecutive 100 ms polls (a failed, malformed or non-processing poll resets the count; a string, a number, `null` or a missing field never counts: the value is compared with `is True`, not tested for truth); the Reader has not completed; no stop is active; the last qualifying poll is ≤ 0.2 s old. The last four conditions are re-validated inside the ledger critical section immediately before the signal (section 4, step 7), not only before the lock is taken. **Token-count fields in `/slots` are recorded as a diagnostic only and never take part** (owner decision; the field is unverified in this build).

**Trigger-miss risk** is addressed by fixture G, not by hope: its expected generation is far longer than P2's 2.1 s, against a 1.5 s arming delay and a ≤ 0.2 s kill delay. Whether a request can be made to run long enough cannot be tested without a real lifetime; **a miss consumes the single pilot** (owner decision 2). There is no calibration lifetime.

## 7. Stop conditions and quarantine

**Inherited from E2-B (unchanged code and thresholds), evaluated by the Driver's monitor:** S1 pressure level 4; S2 pressure level 2 for ≥ 10 s; S3 swap above the phase baseline + 512 MiB for ≥ 10 s; S4 power source not AC; S5 thermal or performance warning; S6 sampler gap or sleep; S7 runtime RSS above the cap; S8 topology violation (a descendant, a group member or a tagged stranger); S9 non-loopback socket or a listener that is not exactly the recorded address; S11 disk below 50 GiB, **lifetime above 300 s** (E3 value), operator interrupt; S12 attendance lapse; S13 a safety observation unavailable (including the monitor thread itself failing). **S10 is not exercised** (the pilot sends no unauthenticated or wrongly authenticated probe). Quarantining stops (S8, S9) persist `owner_review_required` before anything slower and kill the runtime and its recorded descendants by verified identity; strangers are reported and never signalled. **Descendants are retained only through a verified root.** The Driver's observation of a runtime it did not spawn verifies the recorded root (pid, kernel start) live before and again after the inherited enumeration; the descendants found are retained (in memory and in the record) only if both checks pass. Otherwise the whole observation is discarded and reported as unavailable (`lsof_ok` false), because everything it saw would belong to whatever holds the pid now. Emergency kills and recovery add the same rule to their own fresh enumeration, so no unrelated process's child can enter a kill target set; descendants captured while the root was verified stay individually verified targets.

**Actions by phase.** Before the kill: any stop aborts through the live Owner (normal shutdown, policy quarantine carried in the command). After the kill: immediate stops (S1, S7, S8, S9) are executed by the Driver's monitor through the ledger at once; every stop ends the observation window **now**, after which the Successor terminates and verifies. A dead monitor is itself a stop (S13) and ends the window.

**New:**

- **E3-1** No process is ever signalled unless identified by a recorded (pid, kernel start) that the ledger re-verifies immediately before the signal. Violations (a failed pre-kill identity check, an owner kill that was not delivered, an owner that survives SIGKILL, a pre-kill record that cannot be made durable) are stops.
- **E3-2** Topology and socket violations are S8/S9 as above.
- **E3-3** After `t0` the Driver sends no HTTP (the gate raises and counts), and any **new** connection to the runtime seen by the Driver's one-second `lsof` comparison against the list taken immediately after the kill is a stop. Limitation, stated: a connection that opens and closes inside one sampling interval, or in the interval between the kill and the baseline, is not seen by the Driver; the synthetic fixture runtime counts every accepted connection to prove the property in tests.
- **E3-4** First failure ends everything: no retry, no second lifetime, no restart of any role. A failed or unverified lifetime stays `QUARANTINED`; the harness never clears a quarantine.
- **E3-5** An operator interrupt (SIGINT/SIGTERM/SIGHUP) before the kill shuts down through the live Owner; after the kill it ends the window and the termination still completes (bounded); a second signal does not skip it. The handler only assigns to an interruption latch (below), so the latch is converted into the S11 stop before any early exit of the observation loop (Successor ended, backstop) and again when the verdict is derived, which is after the last potentially blocking finalization step (the post-sampling and the final clean-state scan, which enumerates processes and runs `lsof`): a genuine interrupt is never missing from the stop list, and any stop withholds the verdict rows. **Handler and cancellation (all three signals alike).** The SIGINT, SIGTERM and SIGHUP handler is `T.make_signal_handler`: two plain attribute assignments to an `InterruptLatch` (`hit = True`, `signum`), monotonic, and nothing else: no `Event.set()`, lock, call, logging or I/O (a static test asserts the handler contains only assignments). A Python handler runs in the main thread between two bytecodes, also while that thread holds an `Event`'s internal, non-reentrant lock inside `set()` or `wait()`, and a second signal can run a handler inside the first; a handler that called `Event.set()` could block forever on a lock its own thread holds, with the runtime live (reproduced in a child interpreter by a test). The Driver's `interrupted` and `cancel` are `InterruptEvent`s over the same latch: `is_set()` reads the latch without a lock, so every guard (`guard`, `stop_active`, the pre-spawn and Phase 1/2 aborts, the post-sampling) sees an interrupt as soon as the handler has run, and `wait(timeout)` polls in 50 ms slices, never longer than asked and never unbounded where the caller bounded it. A watcher thread (outside the handler, 20 ms period) also `set()`s both Events and any injected ordinary Event. The Monitor's own `cancel.set()` is unchanged. Nested, repeated and under-the-lock signals are tested, including against a live synthetic runtime (before the kill and in the orphan window). **Finalization boundary.** The latch handlers stay installed until the report is sealed, so no signal can end the Driver with a half-written report or skip the termination. The verdict (interpretation, rows, outcome, exit code) is derived in one non-blocking function from the stops as they are then; the raw report and the committed view are then written atomically (temporary file, `fsync`, rename; the committed view carries the raw report's digest), and the flag is read again. If an interrupt was accepted after the verdict's check, the **whole verdict is re-derived** (S11 added, rows withheld, outcome `STOPPED`; an early-phase success such as `GATE_PASSED` becomes `INTERRUPTED`) and the files are rewritten; because the flag cannot be cleared, this takes at most one extra pass. The report is **sealed** at the last of these reads, and states the interrupt state it reflects (`seal.interrupt_seen`, `seal.passes`). An exception in finalization before the verdict is reported by the same rule (an accepted interrupt is S11 in a `HARNESS_ERROR` report). A failure while sealing is **fail-closed** (section 13): the seal confirmation is removed, a pending interrupt is reconciled (S11), every verdict row is withheld, the exit code is 1, `finalize_error` is set, and the outcome becomes `FINALIZE_ERROR` **only if it was a success outcome** (a non-success outcome such as `STOPPED` or `HARNESS_ERROR` is kept, with `finalize_error` set); the report files are then rewritten best effort and remain unconfirmed. An interrupt accepted before the seal is therefore in the report; one arriving after the final read cannot alter a report that is already complete and is outside it by definition (residual 13). An interrupt never kills or quarantines, so it never changes the durable record: the record and the stop evidence stay consistent. SIGKILL of the Driver is a double fault (section 12).
- **E3-6** AC power and operator attendance (S12) are required throughout; lid open; no `caffeinate`, no power-setting change.

Any stop (of any kind) withholds every verdict row (the E2-B D1 rule); observations and counts are kept.

## 8. Signal discipline, races and the backstop

Every signal sent by the Driver, the Successor and the Driver's monitor to an experiment process (runtime, descendants, Owner) goes through the **signal ledger** (`e3_lib.SignalLedger`), which under an exclusive file lock (1) refuses any signal after a SIGKILL to the same (pid, kernel start), (2) allows at most one SIGTERM per identity, (3) re-verifies the kernel identity (pid **and** start time, not a zombie) immediately before `kill(2)`, and (4) appends who sent what, with the time of the actual attempt. The lock wait is **bounded** (2 s): a caller that times out sends nothing and reports `ledger_lock_timeout`, so a stalled holder cannot hold a caller indefinitely; the record store's cross-process writer lock is bounded the same way (`LockTimeout`: the write fails, nothing is written). A caller may pass a `precheck` that runs inside the critical section as the last step before `kill(2)` and can refuse the signal (section 4, step 7). Consequences: the Successor and the Driver (monitor or backstop) cannot both send more than the ledger allows to one identity; a pid that was reused (different start time) is never signalled; every signal is attributable. `os.kill` appears once in the E3 implementation (inside the ledger); a test asserts that no other E3 module calls `kill`/`killpg`, and that no E3 module uses a pid-only helper. Children of the Driver (Reader, Successor) are stopped through their own process handles, which cannot be reused while unreaped.

**Owner abort path (pre-kill shutdown), exact limitation.** The Owner runs the inherited, unmodified E2-B shutdown. Its SIGKILLs (shutdown, `contain`, emergency kill) go through the ledger as `owner`, because the Owner passes the ledger's `kill_fn` to the E2-B `Instance`. Two signals of that inherited code are **not** ledgered: (a) the single SIGTERM of the normal shutdown, sent with E1 `safe_kill`, which re-verifies (pid, kernel start) and the zombie state immediately before `kill(2)` but is neither recorded in the ledger nor subject to its one-TERM rule; (b) `contain`'s kill of an unreaped direct child through its own Popen handle, only when the child's identity could not be read. Justification: the shared E2-B files are not modified (they are bound and byte-identical); the Owner abort path exists only before the owner kill, when the Successor does not exist and the Driver's monitor sends only SIGKILL, so no other process sends a SIGTERM and no duplicate TERM is possible; a later SIGKILL is ledgered and so cannot be duplicated. E2-B's own `term_sent`/`kill_sent` booleans only say that the call was made (they are set whether or not the signal was delivered or the ledger refused it), so the Owner reports them as **attempts** (`term_attempted`, `kill_attempted`); it reports delivery only where it is observable: `kill_delivered_by_ledger` from the ledger, and `term_delivery: not_observable` for the one SIGTERM (the E1 helper's result is discarded by the inherited code; nothing is inferred).

**Attempt accounting is a lower bound.** An attempt that cannot obtain the ledger lock cannot be appended to the ledger. Each process keeps such refusals in memory without pids (bounded) and reports them (the Driver's own; the Successor's final report; the Owner's final report); the report adds them to `attempted` and `refused` (`ledger_lock_timeout`) and shows them apart as `unrecorded`. A signaller that ends before it can report (for example a Successor stopped by the backstop) may have made further refused attempts that cannot be counted, so attempted counts are a lower bound. **Delivery counts are recorded deliveries, also a lower bound.** The ledger entry is appended (and `fsync`ed) after `kill(2)` returns, so a signaller that dies between the two can have delivered a signal that is in no ledger; `delivered` counts signals for which `kill(2)` succeeded **and** the entry was persisted, and `kill(2)` success is acceptance by the kernel, not an effect on the target. A ledger-derived label (`terminated_by`, `exit_cause`) can therefore miss an unrecorded signaller; a killing or quarantining stop with no recorded delivery already yields `undetermined`, and the report is to be read with this in mind. The committed view states this basis (`signals_basis`).

**Residual (documented, not removable on this OS):** between the identity check and `kill(2)` inside the ledger lock a process could exit and its pid be reused by another process within microseconds; macOS has no pid file descriptor. The exposure needs a specific pid to be reallocated that quickly; it is accepted for an attended, single-lifetime pilot. The kqueue exit watch is registered on the verified identity and the identity is re-verified after registration; a process that exits between the identity check and the registration is recorded as `exit_notification_unavailable` (it was seen alive; no notification arrived), not as an observed exit and not as absent at first observation.

**Backstop.** At `t0` + 75 s, or immediately when the Successor exits without resolving the record, the Driver kills the Successor (own child) first so that exactly one signaller remains, then sends SIGKILL to the recorded identities through the ledger, verifies the non-parent conjunction and writes the final state with `cleared_by` = `driver_backstop`; `terminated_by` is derived from the ledger like every other label (section 9), so it is `driver_backstop` only if the backstop's signal was delivered. A pilot that needed the backstop is reported as `PILOT_COMPLETED_BACKSTOP`, and neither O4 nor B4 is informed by it. The Driver never rewrites a record that is already `QUARANTINED` or `EXIT_VERIFIED`; for a `QUARANTINED` record whose recorded process is somehow still alive it still sends the identity-verified SIGKILL (liveness safety) without touching the record. This also holds when the **Successor** is the one that leaves the record `QUARANTINED`: when the Successor has ended, a `QUARANTINED` record triggers the same cleanup (through the ledger, so a SIGKILL already sent to an identity is not repeated and a recorded identity that the kernel no longer confirms receives no signal at all); the attempts are reported (`quarantine_cleanup`: sent or not, with the ledger's reason). **Every post-kill failure path is the same bounded, Successor-first cleanup**: an active stop, a generic exception (including during the orphan observation), the backstop and the final cleanup all stop the Successor (own child, bounded wait) before any ledger or record operation, so a Successor stalled while holding a lock cannot block the Driver's kill or final write (tested for a stall holding the record lock and the ledger lock, with and without an exception in the observation loop). The ledger and the Driver's own writes are bounded, so a failed annotation or refused signal is reported and the safety path continues.

## 9. Truthful non-parent termination classification

The Successor is not the runtime's parent (the runtime was re-parented when the Owner died), so it has **no waitpid**, no exit status and no reaping fact. The E2-B conjunction contained `reaped`; the non-parent conjunction does not, and the record says so. `PROVEN_TERMINATED` (OS-only classifier `classify_os`: the E1 classifier without its application probe, so it opens no socket) requires a bound record with a verified binding, no live process with the recorded (pid, kernel start), no live recorded descendant, no unrecorded live member of the process group, no live process carrying the instance tag, and a usable listener inventory. A final `EXIT_VERIFIED` additionally requires the conjunction `identity_gone ∧ recorded_descendants_dead ∧ group_clear ∧ tag_scan_clear ∧ port_free` to hold at the same time, and no pending `owner_review_required`; otherwise the record is `QUARANTINED`.

The record carries: `exit_basis = non_parent_kernel_identity_and_conjunction`, `waitpid_evidence = false`, `exit_code = null`, and `exit_event`, which is one of three distinct facts: `NOTE_EXIT_observed` (the kernel's exit notification arrived on a watch registered for the verified identity); `exit_notification_unavailable` (the runtime was seen **alive** first and its exit was established by identity and conjunction polling only: no notification was registered or received, e.g. after the Driver's backstop kill, which registers no watch); or `absent_at_first_observation` (the process was already gone at the observer's very first look and had never been seen alive by that observer, **within that observer's scope**; no exit time is claimed). The scopes are: the Successor's first classification; and, for the Driver, its looks **from the kill instant on** (the kill-instant check, the orphan window, its finalizer: `driver_saw_alive_from_kill_instant`). The Driver monitor's earlier, pre-trigger samples are **not** consulted, so the label never says the runtime was not alive before the observer began (the report carries `first_observation_scope`). The Driver's backstop is not the Driver's first observation: it registers `exit_notification_unavailable` whenever the Driver observed the identity alive at any earlier point of that scope (at the kill, in the orphan window). Known limit inherited from E1/E2-B: the tag scan cannot see the environment of Apple platform binaries; descendants are found by parent pid and recorded with their identity.

**Attribution of the exit (O2).** That the runtime is gone does not say why. The cause is read from the signal ledger and the stop state, not from the Successor's own report: `exit_cause` is `SIGNALLED` (some experiment signaller, named, sent a signal to that identity: the Successor, the Driver's monitor or backstop, or the Owner), `UNDETERMINED` (nothing in the ledger, but a stop that kills or quarantines was active: the stops themselves are the evidence, immediate stops that do not quarantine, S1 and S7, included; the record's owner-review flag is only one proxy for them) or `NO_SIGNAL_RECORDED`. `exited_by_itself` is `true` only for `NO_SIGNAL_RECORDED` with the identity gone, `false` for `SIGNALLED`, and `null` (unknown) otherwise. Even `true` means only that no signal of the experiment's own signallers was recorded: the ledger cannot exclude a signal from outside the experiment. **The stop state reaches every writer.** The Driver's finalizer and its report use its actual stops (and the record); the Successor, which reads only the record, uses `e3.killing_stop`, which the Driver publishes in the orphan loop as soon as it sees a stop that kills or quarantines, and the sticky owner-review flag. Publication is best effort and not instantaneous: a Successor that finishes before it is published can label the record `self_exit`; the Driver's report recomputes the attribution from the stops, and `attribution_consistent` is then false. **One label, three views.** `terminated_by` is derived from the ledger's **delivered** signals only (`termination_label`): the single signaller's name (`successor`, `driver_backstop`, `driver_cleanup`, `driver-monitor`, `owner`), `multiple_signallers` if more than one delivered, `self_exit` only for `NO_SIGNAL_RECORDED` with the identity gone, and `undetermined` otherwise. The durable record, the raw `summary.json` and the committed view carry the same `terminated_by`, `exit_cause` and `exit_event`, plus `attribution_consistent` (the recorded label cross-checked against the ledger attribution; a Successor verdict row needs it not to be false). A self-exit is therefore never labelled a Successor or Driver termination and a termination is never labelled a self-exit. **Attempts are not deliveries:** the committed view carries, per signaller, how many signals were attempted, how many were delivered (passed every check and reached `kill(2)`; delivery to the process is not its exit) and the reasons for the rest, without pids. No exit code or waitpid fact is ever inferred for a non-parent.

## 11. Key-file lifecycle and minimum access

1. Created by the **Driver** (never the Owner or Successor), mode 0600, in the 0700 per-run scratch directory, before the Owner starts; the content is never logged or committed. The path appears in the runtime's argv (as in E2-B); the key does not appear in any file the experiment writes (a test searches the whole bench for it).
2. Read by: the runtime (at start), the Reader (in memory, passed on its stdin), the Driver's pre-kill `/slots` polls. **Not** by the Owner (`OwnerInstance.key` is `None`; it only verifies the file's mode and owner), **not** by the Successor.
3. **Deleted by the Driver immediately after the kill signal** and on every error path, including the pre-kill aborts, interrupts and the cleanup that runs last; the deletion does not affect the running runtime (the key is already loaded). The committed view records when it happened relative to `t0` and that the file did not exist afterwards. If the Driver itself is killed, the file survives; `recover` removes it.
4. **Successor access (minimum):** the record path as its only argument; kernel identity/process calls, the listener inventory (`lsof`), the kqueue exit watch, signals through the ledger to verified identities, and locked record writes. Enforced by the kernel: it runs under `sandbox-exec` with `(deny network*)` and with file reads denied on the fixtures directory, the models directory and the run scratch directory. Enforced by tests: the Successor and `e3_lib` contain no socket or HTTP code (static scan), the Successor's imports are an enumerated short list, and the classifier opens no socket even when `socket.socket` is replaced by a function that raises.
5. The Reader receives the key only on its stdin pipe and is killed at the end.
6. Accepted residual (E2-B-like): other processes of the same user can read same-user files and process arguments; the pilot does not defend against a hostile same-user process.

## 12. Recovery and the Driver-failure case

- **Recovery tool.** `e3_harness.py recover RUN_ID` classifies read-only; `recover RUN_ID --kill --confirm RUN_ID` kills the recorded identities (verified pid and start, never by group) and, if the classifier then says terminated, clears the record (E2-B rules). The kill step is E3's own: the E2-B `recover` would enumerate the children of whatever process now holds the recorded root pid, so a reused root pid could make an unrelated process's children "killable". E3 discovers fresh descendants **only** through a root whose recorded (pid, start) is verified live before and after the enumeration; if the root identity does not match, only previously recorded descendants are considered, each verified individually by (pid, start) at signal time, and a quarantine whose identity cannot be established stays a quarantine. The same rule applies to the Driver monitor's emergency kill (a `RemoteInstance` override of the inherited method). It takes the run lock first and so cannot race a live run. It also removes the run's key file.
- **Driver killed before the owner kill:** the Owner sees stdin EOF and runs the normal shutdown, resolving the record; the key file remains until `recover` is run.
- **Driver killed after the owner kill, before the Successor started:** the orphan stays alive until the owner runs `recover --kill --confirm`. **The orphan's lifetime bound cannot be guaranteed after a Driver failure** (accepted, owner decision 5): its natural limits are the runtime's own `-to`/generation cap and attendance.
- **Driver killed after the Successor started:** the Successor, started in its own session, finishes at the deadline recorded before it started (the longest bound, 60 s after the kill), which can be later than a Reader-based shortening; not guaranteed either (for example if the machine sleeps).
- The run lock is released by the kernel when the Driver dies; a leftover non-`EXIT_VERIFIED` record blocks the next run.

## 13. Evidence and committed view

Raw evidence stays in `<bench>/e3/runs/<run id>/` (outside the repository): events, the gate window and context, the monitor series for the whole lifetime, the post-unload window, `server.log`, the signal ledger, the Owner's, Reader's and Successor's metadata lines and stderr, `summary.json`. The **committed view** contains counts, booleans, labels, hashes and numbers only: stops, gate booleans, trigger decision and counters, a timeline relative to `t0`, the Reader's status class, lengths and content hash (no text), the Successor's classification sequence, signals sent, checks and exit class, the sandbox flags, the HTTP-after-kill facts, record state and exit fields (`terminated_by`, `exit_cause`, `exit_event`, `attribution_consistent`), the per-signaller attempted/delivered/refused counts with their basis (`signals_basis`), `owner_review_persisted` and `quarantine_takeover`, the Owner's attempt and ledger-confirmed delivery facts, the verdict rows and observations, the interrupt state the report was sealed with (`seal`) and any `finalize_error`, the tool identities and the raw-artifact hashes. **Evidence acceptance (report consumers).** The report files are **provisional** until sealing is confirmed. The last step of a successful seal writes `seal-confirmation.json` in the run directory: the digests of `summary.json` and `summary-committed-view.json`, the outcome, the exit code the process returns, `passes` and `interrupt_seen`; it is removed before any rewrite and is never written on a failure path. A run's report is a **sealed record** only if the confirmation exists and matches both files (and the committed view's digest of the raw report), the outcome and run identity agree across the three files, no `finalize_error` is present, and the process exit status is known and equals the confirmed exit code. It **supports verdict rows** only if, in addition, the exit status is 0, the outcome is `PILOT_COMPLETED`, no stop is recorded, `seal.interrupt_seen` is false and every raw artifact the view lists still matches its digest. Anything else (no confirmation, a digest mismatch, a missing or contradictory file, a missing or non-zero exit status, a `finalize_error`) means the run is inconclusive or failed: no row of it is evidence, and an earlier success file is never accepted on its own. The check is `e3_harness.py accept RUN_ID --exit-status N` (read-only; exit 0 only when verdict rows are supported), implemented by `e3_lib.evidence_acceptance`. The check also rejects, without raising, a confirmation, raw report or committed view that parses as JSON but is not an object (array, string, number, `null`) or whose `stops`, `seal` or `raw_artifacts` have the wrong structure. **What the acceptance command does and does not establish.** (1) `--exit-status` is an **operator-supplied value** and must come from the actual observation of the process's completion (the shell's `$?` of the `run` command, or the supervising operator's record); the files cannot contain it. The operator records that observed status, and the **exact `accept` command line** used (`python3 tools/evidence/runtime/e3_harness.py [--bench BENCH] accept RUN_ID --exit-status N`), together with the JSON the command returns. (2) `accept` checks the **consistency** of that value with the confirmed exit code and of the files with each other; it does **not** independently establish that the process terminated, or how. (3) The artifact digests protect against **accidental changes and stale files**, not against deliberate forgery: anyone able to write the run directory can regenerate the files and the confirmation. (4) A sanitized committed view is **not self-verifying**, because the confirmation lives only in the run directory: whoever commits or cites a view must accompany it with the `accept` result (the JSON the command prints: `sealed`, `supports_verdicts` and `reasons`; it does **not** contain the exit status), **the observed exit status and the exact command line that produced that result**, the run id and the view's SHA-256, sufficient to associate the result with that exact run and view; or the original run directory must remain available so the check can be repeated. (5) Without valid sealing and an observed normal completion, supporting verdicts must not be accepted; a view that lacks this provenance is provisional. A crash after the confirmation leaves complete files and a non-zero status, which is rejected (fail-closed). `PILOT_COMPLETED_BACKSTOP` and other non-`PILOT_COMPLETED` outcomes can be sealed records but never support verdict rows. **No prompts, outputs, paths, key or home directory** in any committed file. The runtime's `/props` and `/v1/models` expose the model's absolute path (E2-B record §4); the pilot reads neither, and the Driver's only pre-kill read is `/slots`.
