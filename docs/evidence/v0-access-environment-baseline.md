## 1. Authority, evidence boundaries and conclusions

This document operationalizes the configurable gates in the [V0 Access & Security Mechanism Evaluation](../evaluations/v0-access-security-mechanisms.md) (ME). It follows [Project Definition](../00-project-definition.md), [Domain Model](../01-domain-model.md), [Requirements](../02-requirements.md), [V0 Scope](../03-v0-scope.md), [Architecture](../04-architecture.md), [Logical Model](../05-data-model.md), [Security](../07-security.md) and accepted ADRs 0001–0011. See the [ExecPlan](../../.agent/plans/2026-10-04-v0-access-environment-baseline.md).

The selected browser, Tailscale, private-CA HTTPS, same-origin/loopback, passphrase/Argon2id, approved browser credential, opaque session, CSRF and coordinated revocation mechanisms remain unchanged. Eight-hour absolute/thirty-minute idle defaults, no silent refresh, controlled enrollment/recovery, Windows service-user DPAPI/ACL custody and authenticated private runtime access remain in force. Windows co-hosting grants no application authority. FR-15 commit instants, server ordering, provenance and source preservation are unaffected.

Only the Mac executing this task was inspected, using bounded read-only queries. No remote Windows/iPhone access, account login, network probing or configuration was attempted. In the subsequent Mac baseline task on the same date, the user explicitly designated this available Mac as the intended client; the [Mac Client & Alternate Runtime Baseline](v0-mac-client-runtime-baseline.md) records the expanded observations. Versions below are **observed values**, not claims that the latest supported update is installed. No exact addresses, hostnames, account names, serials or secrets are retained.

Evidence labels:

- **REPOSITORY_REPORTED:** Owner-reported intended environment, not independently verified hardware/configuration.
- **OBSERVED_READ_ONLY:** Specific observation on the execution Mac on this date, with method and limits.
- **VERIFIED_FROM_OFFICIAL_DOCS:** Product capability/documented behavior, not our deployment outcome.
- **NEEDS_LIVE_VERIFICATION:** Exact observation remains pending on the intended device.
- **NEEDS_OWNER_INPUT:** A choice/operating preference cannot be discovered automatically. Recommendations are not accepted owner decisions.

The three custody/uptime questions asked during this task have no substantive owner answer yet. “Please continue” authorizes continued work, not a selected custody method. Document completion therefore records owner gates rather than claiming they are closed.

## 4. Owner custody decisions

All C-01–C-07 remain NEEDS_OWNER_INPUT where a choice is requested. Recommended defaults below are proposals for the owner, not new accepted architecture. A usable server secret (TLS leaf/runtime credential protected by DPAPI) is different from recovery material that must survive loss of the server and every client. Anonymous recovery proof, CA signing key, disk recovery key and any future backup decryption key are separate authorities; never reuse one secret for all purposes.

| ID / decision | Options and recommended V0 default | Loss / theft consequences | Blocking point |
| --- | --- | --- | --- |
| C-01 offline CA custody | **Recommend** encrypted removable signing-key package, detached except for an authenticated offline signing ceremony, plus one separately protected offline spare. Decryption material must be retrievable without server/client access. Alternative: reviewed offline signing device; more isolation but added maintenance/hardware availability. A live server folder or cloud-only vault is unsuitable. | Loss of every usable copy prevents renewal; deliberately replace CA/client trust before leaf expiry or remain unavailable. Theft plus unlocking material enables server impersonation and potentially broader trust abuse; close affected access and replace trust. | Before CA/provisioning implementation procedure and any real keys. Abstract API semantics can proceed. |
| C-02 root versus issuing key | **Recommend for owner review** direct offline-root issuance for this single service/three-client V0; fewer keys/procedures, but root is handled at every renewal. Alternative: offline root plus separate protected issuing CA; less frequent root handling, more chain/expiry/revocation work. Never put the root on the live server; an issuing key also remains offline under this proposal. | Lost issuer can be replaced by intact root; root loss is broader. Compromised issuer can forge service certificates; browsers cannot be assumed to honor custom revocation, so root replacement may still be necessary. | Before PKI operational design/provisioning. No hierarchy finalized here. |
| C-03 owner recovery proof medium | **Recommend** two secure paper copies, one away from the shared-house/server/client location. Alternatives: encrypted removable media with independent spare/unlock method; password manager with independently recoverable offline copy. Digital storage eases accurate copying but introduces device/software/backup dependencies. Paper can be read by anyone finding it; no photos/cloud-printing/clipboard history. | All copies lost plus no valid management path means locked retained dataset. Theft supplies recovery proof but still requires trusted host administration; rotate promptly through valid authority. | Before recovery/provisioning workflow implementation and real enrollment, not generic API shape. |
| C-04 redundancy and geography | **Recommend** two controlled copies with different physical failure locations and a private inventory of copy count/custodian/access method. Local separation avoids one theft/fire; distant geographic separation is optional if correlated disaster risk justifies retrieval burden. More copies increase theft/staleness exposure. | One lost copy is survivable with the other. Any missing/suspected copied secret is compromise, not just redundancy loss. Replace retired copies after rotation; do not promise physical secure erasure. | Before custody sign-off; exact location must not be committed. Applies separately to each key family. |
| C-05 disk/machine recovery keys | **Recommend** independent offline recovery copies for Windows disk encryption and Mac FileVault, separate from the protected machine and from ordinary app credentials. Inspect existing escrow first; new cloud escrow is not implicitly authorized. If platform constraints require a different custody mechanism, separately review before private use. | Lost unlocking/recovery methods can make intact ciphertext inaccessible. Theft of key plus disk bypasses at-rest protection; it does not automatically provide a valid Anonymous session. Compromised host/data still requires incident recovery. | Before real private data/OS-secret provisioning; platform integration depends on verified support. Not an API blocker. |
| C-06 server data-loss expectation | **Recommend within current V0 scope** explicitly retain the existing intact-storage process-restart guarantee and no claim to recover a destroyed/lost desktop. If that risk is unacceptable, request a separately bounded backup/restore design before real-data use. No backup destination, schedule, copy or encryption scheme is chosen here. | Owner/CA/disk keys cannot recreate absent source history. A future stolen backup can expose private history/authority if not protected. Restoring stale access state must never revive revoked credentials. | Backup feature design remains deferred. An owner requirement for disaster recovery becomes a real-private-use gate/new task; no silent scope expansion. |
| C-07 custody/renewal operator | **Recommend** owner remains the sole operator, with a private retrieval checklist that does not depend on an authorized browser session. Decide who can access each copy, how to retrieve it during loss, and whether renewal visits are practical. No other custodian is presumed trusted. | Unavailable operator/copies can cause certificate/access outage. An additional custodian changes exposure and must be deliberate, not an invented multi-user role. | Before provisioning/renewal/recovery acceptance; no domain role change. |

When the desktop is lost or damaged, first distinguish unavailable hardware, locked but intact storage, damaged storage and absent source data. Anonymous proof recovers application authority only with intact required state; disk recovery unlocks only recoverable ciphertext; neither restores missing source records. A replacement host cannot activate a copied dataset while the original writer might still be live (section 7). No key export, backup or recovery drill is performed now.

## 7. Exclusive server and dataset ownership

ADR-0011 already requires one authoritative writer and lifetime-held instance exclusion. [ADR-0012](../adr/0012-v0-local-storage-and-authority-transfer.md) records the bounded operational decision added here: V0 production primary state stays on protected server-local storage; copied/restored datasets cannot be automatically activated as independent authorities. It selects no database or lock primitive.

The invariant is one active authoritative application for a dataset lineage, including aliases, stale processes and attempted recovery instances. Identity/installation binding is not merely a directory string or port number. Startup must establish exclusive local dataset ownership and valid installation/access state **before** changing boot generations, admitting requests or writing recovered dispositions. A second instance fails closed with a sanitized conflict; it does not force-unlock, delete a marker or initialize new ownership. Losing trustworthy lock/storage ownership closes protected work; do not continue on a guessed lease or cached allow state.

Persistence/Operations design must specify atomic acquisition, lifetime retention, authoritative lock-loss detection, alias handling, crash cleanup without split ownership, and a recovery protocol preserving access invalidation plus generation uncertainty. A process ID, stale lock file or absence of a listening port alone is insufficient proof of exclusive authority. The selected method must compose with C08 durability and the C03 release coordinator; an implementation binding is still required.

A local lock cannot coordinate two independent offline copies on different hosts. The V0 operating rule therefore prohibits parallel activation of clones and automatic failover: migration/restore remains separately authorized, with the original writer positively stopped and prevented from resuming before a replacement can activate. If the original host's status is unknown, keep the copy inactive. Document the authoritative deployment in protected operator records, not a public hostname registry. Do not claim this procedure prevents a malicious fully privileged operator from duplicating the whole host; distributed fencing/global anti-clone enforcement is not implemented or promised.

Restored old security state must remain quarantined until a separately designed recovery establishes non-revival; fresh boot/session invalidation alone does not repair replayed **device approval** or recovery keys. Recovery must also reconcile surviving runtime/publication evidence before conflicting generation. Existing source facts and commit instants are preserved. No restored dataset or failover is created in this task.
