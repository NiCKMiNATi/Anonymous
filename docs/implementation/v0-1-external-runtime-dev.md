## Scope and unchanged invariants

A dev-only, loopback-only adapter so the existing React/FastAPI conversation flow can talk to an independently launched local llama.cpp server (Qwen3-4B-Q4_K_M, the E2-B/E3 pinned build). It uses the unchanged LD-04 lifecycle: `ConversationService` → `ExecutionCoordinator` → `RunWorker` → `RuntimePort`, with SQLite as the authoritative conversation state.

Unchanged: every LD-04 classification (all runtime-evidence rows stay `BLOCKED_BY_RUNTIME_EVIDENCE`); the SQL schema, triggers, migrations and the store; the domain types and the evidence table; the worker, the router, the scripted and in-process adapters; the client; and all frozen E1/E2-B/E3 evidence, tools, fixtures and pins. The default application still uses `FakeModelAdapter` through `InProcessRuntime`. Synthetic development data only.

## Configuration (real adapter disabled by default)

`--runtime llama-dev` (or `ANONYMOUS_RUNTIME=llama-dev`) **and** `--llama-launch-record PATH` (or `ANONYMOUS_LLAMA_LAUNCH_RECORD`, absolute). Optional: `ANONYMOUS_LLAMA_MAX_TOKENS` (default 384, 1–1024), `ANONYMOUS_LLAMA_MAX_INPUT_CHARS` (default 1400, 1–4000). The dataset must be a canonical `*-dev.sqlite3` path with no `..` and no symlink in it or its parents. Any inconsistency (a record without the runtime selected, an unknown runtime, a bad path or limit) **and a missing, unsafe or malformed launch record or key file** refuse startup before the dataset is created or migrated (`preflight_runtime`); the real adapter never falls back to the fake model. Process liveness is checked per attempt, not at startup.

## Behavior

**Binding.** `EXTERNAL`, `declared_bases = {}`, `late_delivery_excluded = False`, format `llama-dev-http/1`, `instance_ref = llama-<per-launch nonce>`. `stop` is `UNSUPPORTED`; `probe` is `UNKNOWN` (or `INSTANCE_MISMATCH` for a replaced launch), never `CONFIRMED_ENDED`.

**Handoff versus outcome (the UNKNOWN-to-T4 path).** Two different durable facts exist. The *marker* `handoff` goes `NONE → STARTED` in T3b, written by the worker **before** it calls `start` ([worker.py:305](../../server/src/anonymous/application/worker.py#L305), [store.py:766-789](../../server/src/anonymous/adapters/persistence/sqlite/store.py#L766)). The *outcome* `handoff_outcome` records what `start` answered (T3c), after it returns ([worker.py:318-331](../../server/src/anonymous/application/worker.py#L318), [store.py:791-810](../../server/src/anonymous/adapters/persistence/sqlite/store.py#L791)). T4 publication requires the marker, not the outcome: `row["handoff"] != STARTED` in [store.py:832-837](../../server/src/anonymous/adapters/persistence/sqlite/store.py#L832), `OLD.handoff IS NOT 'STARTED'` in the T4 trigger ([SQL:241-244](../../server/src/anonymous/adapters/persistence/sqlite/versions/0002_ld04_execution_ownership.sql#L241)) and `handoff = 'STARTED'` in the assistant-message trigger ([SQL:167-172](../../server/src/anonymous/adapters/persistence/sqlite/versions/0002_ld04_execution_ownership.sql#L167)). None references the outcome. The adapter's `start` writes the whole request and returns `UNKNOWN` ([llama_http.py:203-266](../../server/src/anonymous/adapters/model/llama_http.py#L203)) because HTTP has no acknowledgment before the response; the worker records `UNKNOWN`, treats only `None` and `NOT_STARTED` as "do not wait" ([worker.py:268-275](../../server/src/anonymous/application/worker.py#L268)), and proceeds to `await_result` ([worker.py:281](../../server/src/anonymous/application/worker.py#L281)). A complete response then flows `_handle_delivery` → `_publish` → T4 ([worker.py:359-392, 412-448](../../server/src/anonymous/application/worker.py#L359)). The outcome matters only for *settling* a closed run (admissible bases), where `UNKNOWN` is the conservative value. No `STARTED` acknowledgment is invented and no handoff invariant is weakened. Test: `test_publication_needs_the_started_marker_not_an_accepted_outcome` (persisted `handoff = STARTED`, `handoff_outcome = UNKNOWN`, `succeeded`) and the happy-path adapter test. Before this slice no existing test persisted `UNKNOWN` through to a published response: the closest were the store-level marker test ([test_run_arbiter.py:93](../../server/tests/persistence/test_run_arbiter.py#L93)), the lost-outcome test (outcome unrecorded, [test_handoff_protocol.py:349](../../server/tests/application/test_handoff_protocol.py#L349)) and the `UNKNOWN` closure test ([test_handoff_protocol.py:315](../../server/tests/application/test_handoff_protocol.py#L315)).

**Settlement.**

| Outcome | Result |
|---|---|
| HTTP 200, `finish_reason: stop`, nonempty, process identity unchanged, labels equal | T4: message saved, run `succeeded`, slot free. T4 stamps `runtime_reported_terminal`, which for this binding means *accepted response delivery*, not process termination and not B3 qualification |
| `length`, empty, other finish reason, model-label mismatch, response not saved | closed, `indeterminate`, slot quarantined; nothing settles through B3/B4/B5 |
| HTTP 4xx/5xx, malformed, oversized, truncated or ambiguously framed body, dropped connection, wrong key, deadline, endpoint or identity changed during the request, partly written request | `POSSIBLY_ACTIVE` → closed, quarantined |
| Late delivery after closure, lost publication race, undeclared probe result | ignored by the guard; the run stays quarantined |
| Connection refused before any byte, or the listener not the recorded process immediately before dispatch | `NOT_STARTED`: B2 `adapter_never_reached`, run `failed`, no quarantine; neither prompt nor key was sent |
| Launch record or process/listener unverifiable, input over `max_input_chars` | not dispatched (B1), run `failed`, no quarantine |

**The rule, enforced twice.** `basis_permitted_for_binding` (domain, pure): an `EXTERNAL` binding may rely on B3/B4/B5 only if declared. `RunSettler.apply_evidence` ([settling.py:78-110](../../server/src/anonymous/application/settling.py#L78)) refuses otherwise and `_verify_and_settle` filters its admissible set; **the store enforces the same rule inside the transaction shared by `settle_in_flight` and `settle_indeterminate`**, returning `NO_ADMISSIBLE_BASIS`, so a direct caller cannot bypass the settler. Every B3-shaped path reaches the settler check, and a structural test pins that: the store's two settlement writes are called only from `apply_evidence`, and `apply_evidence` is called only from `_settle` and `late_delivery` (settler) and `_settle_known` (worker). No migration was needed. Owning-process and fully declared bindings, B1 and B2, and normal T4 publication are unchanged.

**Attribution.** Before anything is written, `start` re-verifies that the recorded (pid, start) is live **and** the sole listener on the exact address (a prompt or key is never sent to a mismatched listener); before a response is accepted it re-establishes both. The bearer key keeps other local clients away and is never evidence of the responder's identity. **Residual race:** a swap between a check and its use is caught only if it persists to the post-response check; a process that answers and then restores the original listener, and a hostile same-user process, are outside the localhost development threat model. Stronger attribution (the owner of the established socket) would be a larger change.

**HTTP framing.** A response is accepted only with a fully received single `Content-Length` or a complete chunked coding, under the size bound. A short body (which `HTTPResponse.read(n)` returns silently), a truncated chunked body, a close-delimited body, an invalid `Content-Length`, **more than one `Content-Length` header (identical or conflicting)** and `Content-Length` with chunked coding are all rejected. `http.client` parses only the first `Content-Length` into `response.length`, so repetition is detected from `response.headers.get_all("Content-Length")`, not from `getheader()`.

**Launcher and cleanup.** `launch` validates the record path first (absolute, canonical, no `..`, no symlink), exclusively creates and syncs a launch-intent file (`O_EXCL`; this is the first artifact created), then spawns the pinned profile (no-fork sandbox, `127.0.0.1`, allow-listed environment, per-launch key file 0600 in a 0700 directory, own session). Any failure between the spawn and the durable record is contained through the `Popen` handle (identity-safe while the unreaped child is held); key, intent and log are deleted only if the child is confirmed gone, otherwise all are retained and the pid and start identity are reported. **Artifact ownership:** the launcher deletes only files it created itself. A launcher that loses the `O_EXCL` race for the intent refuses (`unresolved_launch_intent`) and never touches the winner's intent. **Uncertain spawn:** if the spawn was entered but returned no handle (an interrupt during `Popen`), a child may exist, so the tool refuses with `spawn_status_unknown`, keeps the intent, key and log, and prints the nonce and port (no pid is claimed); an `OSError` from `Popen` means exec failed and nothing was started, so the launcher's own files are removed. An interrupted or killed launcher leaves the intent, which blocks further launches and makes `status`/`stop` refuse (`launch_intent_without_record`, with the nonce and port in the refusal) until an operator resolves it by the procedure below. `stop` sends SIGTERM to one process only if its recorded (pid, start) is live, re-checked just before the signal; it refuses on a mismatch (exit 3), never signals a group or a port holder, never escalates, and cannot reach SQLite. **An inconclusive inspection is not absence:** `identity_of` returns `None` only on a positive `ESRCH` and raises `IdentityUnavailable` otherwise; the tool then deletes nothing, replaces no record and signals nothing. Errors are printed by code, never by path. It settles nothing.

**Remaining unavoidable window.** A process termination that cannot be caught (SIGKILL, power loss) or a signal delivered in the few bytecodes between `Popen` returning and the containment `try` starting leaves a possible unrecorded child that this tool did not contain. What remains is durable: the synced intent (nonce, port, key-file path), the key file and the runtime log, which together identify the child by the nonce in its command line. The record itself is written with an atomic rename but is not fsynced (a power loss, not a process kill, could lose it).

## Recovery from a retained launch intent (`launch_intent_without_record`, `unresolved_launch_intent`, `spawn_status_unknown`, `runtime_may_survive_unrecorded`)

This is an operator procedure on the world. It changes nothing in SQLite, settles no run and releases no quarantine; a quarantined dataset stays quarantined.

1. **What the retained intent identifies.** `<record>.intent` (0600, in the private record directory) holds the launch's `nonce`, the intended `port` and the key-file path. It does **not** hold a pid or start time. The refusal printed by the tool repeats the nonce and port (never paths). The runtime, if it was started, carries the nonce in its own command line as `--api-key-file …/key-<nonce>`, so the nonce identifies that process uniquely. Do not look for it by process name or by port alone.
2. **Locate candidates by the nonce.** List processes with their full command lines and start times and select only those whose command line contains `key-<nonce>` (for example `ps -axww -o pid,lstart,command`, filtered for that exact string). Optionally cross-check that the port in the intent has a listener (`lsof -nP -iTCP:<port> -sTCP:LISTEN`) belonging to the same pid; that is a cross-check, never a selector.
3. **Verify uniqueness and identity before signalling.** Proceed only if exactly one process matches, its command line also shows the intended `--port <port>` and the loopback host, it is owned by you, and its start time is consistent with the launch attempt (the intent's creation time is in the file). Note its pid and start time. Immediately before sending anything, repeat the selection and confirm the pid and start time are unchanged. Then send SIGTERM to that one process (never a group, never `kill -9` as a first step, never by name).
4. **If identity is uncertain** (no match, more than one match, a mismatch of port, owner or start time, the listing or `lsof` failing or timing out, or a changed pid between the two looks): do not signal anything and do not delete anything. Keep the intent, key and log, and treat the dataset as unusable until a human resolves it. Absence of a match is only evidence of absence if the process listing itself succeeded and was complete; if in doubt, wait for the host to be idle and repeat the listing, or restart the host.
5. **When the retained files may be deleted.** Only after either (a) the single verified process was terminated and a fresh listing shows no process with that nonce, or (b) a complete, successful listing shows no process with that nonce and no listener on the intended port belonging to this user. Then delete, in this record directory only, `<record>.intent`, `key-<nonce>` and `runtime-<nonce>.log` (and a stale `<record>` for the same nonce if one exists). Never delete them while a matching process may exist: the key file is also the evidence that identifies it.
6. **Afterwards.** A new `launch` may proceed. Any Anonymous run that was open when the launcher or the runtime died is handled only by the existing lifecycle: this procedure neither settles it nor frees the slot, and a restart or a new launch must not be used to escape a quarantine (the supported recovery is a new `*-dev.sqlite3` file).

The same procedure applies when the tool reports `runtime_may_survive_unrecorded` (it also prints the pid and start time it held; verify those against the listing instead of the nonce lookup) and `spawn_status_unknown` (no pid is known; use the nonce).

## Limitations

- **Permanent quarantine of the disposable dataset.** Any rejected, ambiguous or failed response (a `max_tokens` cut-off, an empty reply, an HTTP error, a deadline, a crash, a shutdown during generation) quarantines the single slot for every conversation, across restarts. There is no release, reset or force path; the supported recovery is a new `*-dev.sqlite3` file (the old history stays readable). Stopping the runtime does not change this.
- The 1400-character cap is a proxy for the 2048-token context; a real overflow returns an HTTP error and quarantines.
- Identity facts are macOS-only (libproc, `lsof`). A (pid, start) check followed by a signal has a short but **unbounded** reuse window (scheduling or suspension can lengthen it).
- Response attribution is bounded by the localhost development threat model (see Attribution): a listener swapped and restored around a request, or a hostile same-user process, is not detected.
- A launcher killed (or a host that loses power) between the spawn and the record leaves only the intent, key and log; recovery is manual by the nonce procedure above. The retained evidence is durable but not self-executing, and there is no pid in it.
- The SQL trigger still does not check `declared_bases`; the rule is enforced in Python by the settler and the store (a trigger check would be a migration).
- Digests from pins are `asserted`; the `model_label` check is a configuration constant, not model identity.
- A surviving runtime keeps generating and discards the output (E3 O5); only `stop` ends it, and it settles nothing.
- The runtime's own log and the launch record hold local paths; they stay local and are never committed.

## Operating conditions of the first attended smoke

These are limitations of the first attended run, not properties the software enforces:

- **Synthetic data only.** The dataset is a disposable `*-dev.sqlite3`; the real adapter must never see personal conversation data.
- **Loopback only**, one runtime on `127.0.0.1`; no other endpoint is requested; the bearer key is not an identity proof.
- **Attended launcher lifecycle.** A person starts the launcher, watches it to its record, runs the smoke and stops the runtime with `stop`; the launcher is not left unattended and is never killed while launching. After any abnormal exit, check for a retained intent and use the recovery procedure before launching again.
- **No concurrent competing launch.** One launcher, one record directory, one runtime at a time; a second launcher losing the intent race refuses and leaves the first untouched, but concurrent launches are not a supported mode.
- **No production PRIVATE-mode security claim.** Attribution rests on kernel facts checked before dispatch and before accepting a response; the residual race and a hostile same-user process are outside this threat model. Connection-level peer attribution would be needed before any PRIVATE or non-development use.
- **No real model execution before separate authorization.** Everything here was verified on simulated HTTP and stand-in processes. The real launcher, sandbox and Qwen behavior stay NOT TESTED until the owner authorizes one run.
- **Fresh disposable development database** for the run.
- **Identity-safe cleanup and post-run inspection.** Stop only through the tool, then inspect: no process with the nonce, no listener on the port, no retained intent, and a sanitized record of the outcome.
- **No restart or reset to silently escape quarantine.** A quarantined dataset is finished; the recovery is a new dataset file, never an edit, a restart trick or a relaunch against the same slot.
