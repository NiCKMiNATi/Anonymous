# v0.1 — first local-model chat through a dev-only external llama.cpp adapter

## 1. Title, status, and purpose

**Status: IMPLEMENTED, REMEDIATED after the first independent review and patched after the focused re-review (PASS WITH CONDITIONS, conditions resolved); development only. The sections below keep their historical wording where it describes the earlier state (ADR Proposed, smoke not started).** Record: [implementation record](../../docs/implementation/v0-1-external-runtime-dev.md).

**Problem.** Slice 0B-1 runs the full execution lifecycle only against a scripted, in-process runtime. The owner wants the first usable Anonymous conversation with the local Qwen3-4B model, reusing the React and FastAPI flow, keeping SQLite authoritative and PRIVATE data local, without misrepresenting an external process as owned and without weakening an accepted invariant.

**Outcome.** A disabled-by-default adapter that talks to an independently launched, loopback-only llama.cpp server, a dev launcher/cleanup tool, and a narrow settlement guard, so a conversation can complete and every non-clean outcome fails closed.

## 3. Requirements and acceptance criteria

Done when (all met on simulated HTTP unless marked): the default configuration still uses the fake model; the real adapter needs explicit configuration and a canonical `*-dev.sqlite3` dataset; a complete, attributable, nonempty, accepted response publishes through T4 and history persists; rejected, ambiguous, failed and late responses cannot release a quarantine through B3/B4/B5; the binding is `EXTERNAL` with no declared bases and `late_delivery_excluded = False`; scripted and in-process behavior is unchanged; only `POST /v1/chat/completions` is requested; no key, path or prompt reaches logs or run records; the launcher and cleanup refuse identity mismatches and never reach SQLite; the existing 302 tests, ruff and strict mypy still pass. **Not met (by design, pending authorization):** a real launch, a real Qwen response, an end-to-end browser conversation.

**Non-goals:** streaming, cancellation, personas, memory, Windows, new runtime experiments, any LD-04 reclassification, a force release or reset, a schema migration, use with personal data.

## 4. Constraints and open questions

Constraints from the owner: successor-side B4 must not by itself release an external binding; the owner performs all Git staging and commits.

Open (each blocks only what is stated): **Q1** owner acceptance of ADR-0015 — *resolved: accepted by the owner, committed `6a6ad1c`*; **Q2** a separate authorization for the attended smoke — *resolved for the first smoke: authorized, run once, closed as completed with deviation and quarantine; any further smoke needs its own authorization*; **Q3** whether a later ADR should provide any release or recovery path for a quarantined dev dataset (blocks nothing now; today recovery is a new dataset, which the first smoke made concrete: the quarantined dataset kept two accepted replies readable but cannot continue the conversation); **Q4** a store-level `declared_bases` check (needs a migration; deferred); **Q5** whether the 1400-character input cap and `max_tokens` 384 suit real use — *the smoke gave a first data point and does not settle it: the cap did not intervene (717 characters of history at the third turn), but `max_tokens` 384 was reached on the third turn of a short conversation and quarantined the dataset*. **Configuration step done 2026-10-24 (guard only): the two caps must now fit the pinned 2048-token window jointly; the defaults were deliberately not moved. Q5 is NOT resolved**: the likelihood of a `length` cutoff is unchanged, and lowering it by configuration alone only trades away input capacity (§9).

## 5. Affected components and intended approach

Data flow is unchanged: client → `POST /api/v1/conversations/{id}/messages` → `ExecutionCoordinator` → `RunWorker` → `RuntimePort` (new adapter) → loopback `llama-server`. Source of truth is SQLite; the model response exists only in memory until T4. The adapter attaches to a runtime launched independently by `anonymous-llama-dev`, whose launch record (outside the repository and SQLite) carries the pid and start identity, nonce, loopback address and key-file path. Files created and changed are listed in the implementation record. No migration or recovery change: a quarantined run is recovered only by a new dataset.

## 9. Discoveries

- Two durable handoff facts exist: the marker (`handoff`, T3b, before `start`) and the outcome (`handoff_outcome`, T3c, after). T4 depends on the marker only, so an `UNKNOWN` outcome does not block publication. No pre-existing test persisted that combination through to a published response.
- Every B3-shaped settlement path funnels through `RunSettler.apply_evidence`; one guard there covers all of them. The router filtered `declared_bases` only for probe results.
- Non-daemon worker threads mean a test that arms a runtime gate must release it in `finally`, or a failing assertion hangs the interpreter at exit (this explained the hanging mutation run).
- Under the owner's rules a plain `finish_reason: length` quarantines the dev dataset permanently.
- The independent review found what the author's tests missed: `HTTPResponse.read(n)` returns a short Content-Length body without raising; a listener check in `prepare` is stale by dispatch; `proc_pidinfo` failure is indistinguishable from absence unless `errno` is read (only `ESRCH` is absence; a process of another user gives `EPERM`); the store can enforce the declared-basis rule in Python with no migration. Writing the F1 tests also exposed a leftover log file in the containment path (fixed).
- The runtime's own responses and log expose the absolute model path (E2-B), so the adapter reads no metadata endpoint and the runtime log stays local.

**After the first attended smoke (2026-10-24, n=1; [evidence](../../docs/evidence/v0-1-first-real-qwen-smoke.md)).** Observations, not guarantees:

- The real chain worked once (launcher, sandbox, identity facts, `--hash`, real response shape, T4 publication from an `UNKNOWN` outcome, persistence across a server restart, identity-verified stop). The H2 hazard (the launcher declares readiness at the listener, not at model load) did not materialize (`/health` 200 on the first poll) but the committed CLI still has no model-ready check.
- The owner sent three messages, not one (deviation). The third generation reached `max_tokens` 384 (198 prompt, 384 generated tokens, 9.8 s): rejected by design, closed `indeterminate` with `closure_reason = runtime_failure`, dataset quarantined, unchanged by a restart. The persisted row does not say *which* rejection occurred, because `failure_code` must be null for `indeterminate` and `closure_reason` is a closed set (a migration would be needed to persist it).
- The model told the owner it ran "in the cloud". That is model output about an environment it was never told about: a later runtime-context and product-quality topic (the context is `ContextBuilder`, golden-pinned, so any change is a new context version under ADR-0014), not evidence of external network use (sandbox denies outbound except localhost).

**Q5 assessment (read-only; proposals pending an owner decision, nothing implemented).** Code: `llama_http._parse_chat_response` sets `Completed.complete = (finish_reason == "stop")`; `worker._handle_delivery` refuses `not delivery.complete` and `_settle_known("output_truncated")` calls `RunSettler.apply_evidence`, which ignores B3 for a binding that declared none (`domain/evidence.basis_permitted_for_binding`), so `close_and_verify(RUNTIME_FAILURE)` leaves the run `indeterminate` and `store.generation_state()` blocks every conversation. Already distinguishable in the data: `runtime_failure` means the bound instance *delivered* a response that Anonymous rejected, whereas no response arrives as `connection_lost` or `deadline`. The adapter has complete, unambiguously framed, identity-checked knowledge for a `length` response and none for a dropped, timed-out, errored or listener-changed request, so the two classes can be kept apart without any B3/B4/B5 claim. Neither a `stop` nor a `length` response shows the slot idle: T4 already means only "accepted response delivery" (ADR-0015 point 1). Levers, smallest first: (1) *configuration*: `ANONYMOUS_LLAMA_MAX_TOKENS` (1–1024) must be sized with `max_input_chars` against the pinned 2048-token context; at the 1400-character cap a worst-case one-token-per-character input leaves roughly 600 tokens, so a larger `max_tokens` needs a lower character cap or token-aware accounting (the adapter must not call `/tokenize`); `validate_runtime_settings` could reject combinations that cannot fit; (2) *brevity*: a context change (new version, ADR-0014); (3) *policy*: accept a complete `length` response through the existing T4 path as a visibly truncated assistant message. (3) uses the existing success evidence class and invents no basis, but it reverses ADR-0015 point 2 for one finish reason (the owner rejected settling truncated responses in revision 1; this does not settle, it publishes), needs `Completed` to carry the finish reason instead of a boolean, a durable truncation marker (messages are immutable and have no such field; `completion_observed` is a closed set, so a migration), a client indicator and an ADR revision. **Minimum slice proposed:** an ADR revision or successor deciding (3), preceded, if the owner wants relief immediately, by lever (1) as a configuration-only change with its validation test.

**Q3 assessment (read-only; proposals pending an owner decision, nothing implemented).** Code: `store.generation_state()` treats any epoch-`0b` `indeterminate` run as a global quarantine (health reports `runtime_quarantined`; admission raises `RuntimeQuarantined`); `reconcile` re-verifies on startup and, with no declared basis, keeps it (observed: unchanged across a restart); `messages` and `model_runs` are immutable or undeletable by trigger. A release, force-release, operator attestation or cleanup-produced B4 is rejected by the owner and CB-05 and needs its own ADR; it must not be smuggled in as "reset". Smallest safe recovery that discards no history and releases nothing: keep the quarantined dataset as read-only source history (already readable), start a new `*-dev.sqlite3`, and provide a **read-only transcript export** of the quarantined dataset (messages in position order with ids and commit times, run status and closure reason, no key or path) so the owner can carry context forward by hand. A real *carry-forward* (import as a new conversation with source ancestry, INV-003/005/006) is a later slice: an assistant message requires a producing run (`messages` check), so imported assistant text needs an explicit imported-source provenance in the domain, which touches the open branch/derivation design (domain model §§10–12) and needs a decision first.

**Q5 configuration step (2026-10-24; implemented, see the [implementation record](../../docs/implementation/v0-1-external-runtime-dev.md)).** Traced: the launcher pins `-c 2048 -np 1`; the worker counts input in characters only; the two limits were validated independently, so pairs that cannot fit (1024 with 1400, 384 with 4000) were accepted. Implemented: a joint check with a 256-token template allowance, defaults unchanged (spare 8 at 1400 + 384), a test pinning the constant to the launcher's `-c`. Why the defaults were **not** raised: under the character proxy the window is zero-sum (input 1400 allows at most 392 output tokens; 1000 allows 792); history includes the assistant's replies (about 4.3–4.6 characters per token in two observed replies, so a reply near 384 tokens is already about 1,650–1,750 characters, above the 1400-character input cap for the next turn); moving the split trades quarantine-class failures (`length`) for refusal-class ones (`context_exceeds_capacity`, a B1 failure, no quarantine, but the conversation cannot continue) and three observations cannot say which the owner's usage prefers. A real reduction of cutoffs without that trade needs a contract-level decision, not configuration: (a) token-aware input accounting (the adapter must not call `/tokenize` today: ADR-0015 point 9), (b) a larger `-c` in the launch profile (changes the measured E2-B/E3 profile and pins; KV memory evidence needed), or (c) accepting a complete `length` response through T4 as a visibly truncated message (reverses ADR-0015 point 2 for one finish reason; needs an ADR revision, `Completed` carrying the finish reason, a persisted marker, a client indicator). The guard also does not make non-single-byte text safe (a token never covers less than one byte, characters understate bytes) and real context overflow behaviour of this build is untested.

**Q5 visible truncation (2026-10-24; implemented per the owner's approval of ADR-0016).** A complete, attributable, non-empty delivery with the exact finish `length` now publishes through T4 with message completeness `truncated`; the quarantine for that case is gone, every other ADR-0015 quarantine condition is unchanged, and no B3/B4/B5 meaning changed (T4 still means accepted response delivery). Persisted as `messages.completeness` (migration 0003, nullable, no backfill, immutable, atomic with T4); shown by the client from the persisted message only. Findings while implementing: (1) the scripted runtime re-wraps every result without the new mark, so scripted `Completed(complete=False)` keeps its old outcome without any change to it; (2) `complete=False` alone cannot be treated as truncation (unknown or missing finish reasons would be accepted), so the port carries an explicit mark and rejects the contradictory combination at construction; (3) existing tests that pinned the schema version (2) or listed message columns with `SELECT *` had to move to version 3 and an explicit 0001 column list. **Not resolved:** the 1400-character history cap is a separate limitation that accepted truncated replies reach sooner, bounded context selection is not built, and the behaviour had not run against a real model when this was written (since observed once, see §11).

**Update 2026-10-25:** bounded recent-history context was implemented as a separate slice, see [the ADR-0017 ExecPlan](2026-10-25-v0-1-bounded-recent-context.md); it does not change the Q3 or LD-04 conclusions below.

**Recommended smallest v0.1 usability improvement:** the Q5 policy decision on complete `length` responses (it removes the dominant failure mode at its source and needs no new evidence basis), with the read-only transcript export as the independent, smallest Q3 slice. Neither is started.
